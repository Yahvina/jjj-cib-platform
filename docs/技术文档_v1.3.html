零、方法框架：一条政策到模型参数，要走三跳

后面按功能点逐项说明，但那些功能不是并列的十个模块，而是同一条链上的不同环节。先把这条链说清楚，每一块才知道自己站在哪。

环节动作产物回答的问题例子
第一跳定性映射描述符这条政策动哪个变量？「工业差别电价」→ 单位产品能耗限额强度
第二跳定量换算状态区间这个变量取多少？「河北电炉炼钢 2030 ≥15%」→ 短流程占比这一档的落点
第三跳模型翻译模型参数怎么写进 GCAM / CHEER？→ share-weight、技术上限 / 下限、投资成本曲线

三跳各自靠什么，难在哪

第一跳：靠判断，判据是"模型里有没有这个变量"

这一跳没有算法，是人的判断，所以会错。判据只有一条：模型里有没有一个变量，装的就是这个描述符要设定的那个量。

  • 有，且就是它 → 政策直接落在这个变量上
  • 有，但装的是系数 / 曲线 / 潜力 → 属于间接影响，需要说明路径
  • 没有 → 说明这个量不是模型的内生变量，政策只能通过别的变量间接起作用

之所以要死守这条判据，是因为一旦放宽成"这条政策涉及哪个领域"，映射就会散——建筑能效标准会被连到"产业结构"，因为建筑属于产业；但它实际改的是建筑能效标准，不是产业结构。这在双边核对里已经出现过（见「三、下一步计划」）。

第二跳：靠算术，难在分母

政策文件给的是目标的自然口径，模型要的是它的口径，两者常常不是一回事：

政策给的区间要的缺什么
北京外调绿电 650 亿 kWh（2030）占全社会用电 %当年全社会用电量
森林覆盖率 45%（2030）碳移除 万吨/年林地面积、单位面积碳汇系数
可再生装机 8 GW（2025，天津）占一次能源 %利用小时数、总发电量
数据中心 PUE ≤1.15节能建筑占比不是同一个量，需要另找目标
炼化成品油占原油加工量 ≤40%三产占比不是同一个量，需要另找目标

要分清两种"不能直接用"：前三种是同一个物理量、单位不同，除一个分母或乘一个系数就能对上；后两种是压根不是同一个量，换算是换不出来的，只能另找直接目标。把这两类混为一谈，会得出"所有政策目标都能换算"的错误结论。

第三跳：靠文献与试跑

同一个政策目标，写进 GCAM 和写进 CHEER 的落点完全不同——GCAM 里多是市场份额权重与技术上下限，CHEER 里多是税率、转移支付与要素供给。这一跳在平台里体现为「翻译动作」与「目标模型」两屏，具体参数取值需要文献依据与试跑校准，不属于本平台的自动化范围。

区间上的四个徽标，说的就是这条链走到哪

徽标含义在链上的位置
政策目标政策数字的口径与区间一致，可直接用第二跳已完成
需换算有政策数字，但口径不同第二跳卡在分母
示例值政策文件里找不到对应目标第一跳有、第二跳无据
外生输入由 SSP 情景给定，政策不驱动不在这条链上

这个分法的用处不是给区间贴标签，而是把"判断"和"算术"分开：第一跳是判断，可能错，要双边核对；第二跳是算术，只要分母有出处就可以复算复核；第三跳是工程，靠试跑验证。三类问题的排查方式完全不同，混在一起就只能笼统地说"还有待完善"。

通用性与落地：一套引擎，两层底料

这一节回答一个容易被误解的问题：这个工具到底是不是只能做京津冀？

面谈里的原话是两层意思，并不矛盾：

  • 方法要通用：「我的目标不是要收集政策，而是任何人、任何地区，京津冀无论是城市、县乡，给我一个政策文本，我上传那个文本，它自动就解译成对应的结构化的描述符体系。」（第 65 段）
  • 卖点要落地：「德国人开发的那个用户界面，相当于一个通用型工具。我们相当于在它这个基础上，怎么又加上京津冀的本土化数据……咱卖法就不只是一个通用算法了。」（第 345 段）
  • 更直接的一句：「别人为啥绕不开咱？绕不开咱这个工具的原因，是因为你这里面有京津冀本地化的数据——他不用自己再去找数了。」（第 323 段）

所以定位是「通用引擎 + 本地底料」：

层内容是否可替换
引擎CIB 一致性检验、状态级精判、数值锚定、跨层校验、逐层求解、路径分析与地区无关，换任何区域都照跑
底料19 个描述符、55 个状态、106 条政策路径、三地政策目标与统计口径可整套替换——这正是「分类框架可替换」这条待办的含义
案例京津冀绿色低碳发展路径SRT 的验证案例，不是方法边界

一句话：方法本身能搬到任何地区，但搬走之后要重新配底料；而京津冀这套底料（描述符体系 + 政策路径 + 三地目标值 + 分省区间）就是别人绕不开的部分。这也解释了为什么「通用性」与「落地」可以同时成立——通用的是算法，本地化的是数据。

工程上的直接推论：平台上所有预设（描述符树、政策路径、区间、依据）都应当是可替换的配置，而不是写死在代码里。目前描述符与政策路径已是数据表形式，但「一键导入另一套分类框架」的界面尚未做——见「下一步计划」。

1　政策库与映射

解决什么问题

"功能界面上要加载一个政策库……从京津冀的一个政策库，咱相当于自建了一个……可以给它保留窗口，用户可以自己上传这个政策，也可以自定义这些政策。但我们初始的已经做了一些，相当于测试用例，这样让别人一下就觉得咱这软件一看就是针对京津冀地区的。"

层级树怎么搭：4 层，但只有 3 层参与枚举

层级树由三层（国家 / 省 / 市）改为四层，新增「区域级 = 京津冀」。区域级不是可有可无的一层——没有它，"三地加总"就没有可比对的落点：三省之和只能跟全国比，而京津冀只是全国的 3/31，这个比法从前提上就不成立。

同时要分清一件事：层级树里的层，不等于参与枚举的维度。

层级角色理由
国家级给定层（不枚举）取值来自国家政策目标（如 2030 非化石目标），是外部条件。你不会去问"国家该定多少"，只问"在这个目标下区域怎么走"。
区域级（京津冀）决策变量三地合计口径，是省级加总的落点。
省级决策变量北京 / 天津 / 河北各自取值。
市级决策变量河北 11 市（京津下级缺位，见边界一节）。

为什么保留国家级：国家目标确实硬约束区域——"2030 非化石 25%"是写死的，丢掉这一层就丢了政策传导的起点（国家目标 → 区域分解 → 省市落实）。但它既然是给定的，就不该当变量去搜。

省下的组合数是实打实的：按 6 个描述符、每层 3 档估算，4 层全当变量是 3²⁴ ≈ 2824 亿，去掉给定层是 3¹⁸ ≈ 3.9 亿——差 729 倍（正好 3⁶）。多一层变量，组合数乘 3^描述符数；多一层给定，一个组合都不多。

怎么实现

  • 数据层：把政策数据集的 106 条路径（89 条来自 CCPID 国家库、17 条为京津冀地方补充）导出成 JS 常量 POLICY。每条带类别、组别、缩写、排放部门、工具数，以及它对应到模型的哪些描述符——对应关系含置信度（高/中/低）与依据文字。
  • 界面层：左侧按类别分组的路径列表，支持按类别、按"有无对应描述符"筛选；每条右侧的小数字是它命中的描述符个数（灰色 0 表示不落在本模型口径内）。右侧面板：选中路径后显示其对应的描述符与依据；未选中时显示政策库对 19 个描述符的整体覆盖情况。
  • 两个动作：applyPolicy() 按映射给已选描述符回填来源说明；uploadPolicy() 读入用户自己的 CSV 清单（格式：类别,组别,路径,部门）。

2　交叉影响打分（含 AI 预填与人工审核）

解决什么问题

"那你没有一个评分的过程啊，评分不是描述符和描述符的不同状态之间这个影响啊？……GDP 增速高的时候，对人口收缩，三分二分一分还是负一负二负三，这个都没有。"

"还得有一个吧……你现在有一个 agent 可以打分啊，就是人机协同啊……应该是让那个 agent 先填一版出来，然后有人来审核。"

"AI 可以给出一个，他说可以打 3 分、打 2 分也好，有个依据让人来（审）……这样的话人就会把精力放在那个低执行度的角度来进行 check。"

怎么实现

  • 矩阵：n × n 网格，非对角线为判断格，分值 −3 至 +3 并按强度着色。注意两个方向分开判断——官方手册第 2.2 节明确"A 对 B 的影响"与"B 对 A 的影响"是两件事，因此待判条数为 n(n−1) 而非 n(n−1)/2。
  • 数据结构：cim['源>目标'] = {v:分值, conf:'高|中|低', why:'依据', rev:是否已审核}。四要素齐备，是"可追溯"的最小单元。
  • AI 预填：aiFill() 依据内置的 38 条强关系表 AIRT 填出一版，每条都带依据与置信度；未命中的格子给 0 分并标注"待人工判断"。
  • 人工审核：点击任一格打开侧栏，可改分值、定置信度、写依据，并标记为已审核（留痕）。筛选器可按"仅低置信度""仅未审核"过滤，统计栏实时显示应判/已填/低置信度/已审核/待审核。

过去平台只有"自洽情景里的一条判断链"，没有独立的打分屏。现在导师指出的这个空档补上了，而且把"AI 预填 → 带依据与置信度 → 人只审存疑项"这条机制做成了可操作的界面——AI 填完一版后，人打开筛选器只看低置信度的格子即可。

3　自洽情景计算（CIB 一致性检验）

解决什么问题

这是 CIB 方法的本体。v1.0 里"矛盾组合数""自洽情景数"是编的，必须换成本方法真算出来。

怎么实现

  • 状态级影响值：由描述符级分值按两端状态的高低位置展开—— 影响值 = v × (2p_a − 1) × (2p_b − 1)，其中 p 是状态在"由高到低"序列中的归一化位置。含义是：正向影响下，源状态越高、目标状态越高，促进作用越强；源高目标低则表现为抑制。
  • 枚举与判定：runCIM() 遍历全部状态组合（组合数＝各描述符状态数之积）。对每个组合、每个描述符，累加其他描述符对它的影响，得到该描述符各状态的影响平衡值；若选定状态不是最高分，该组合不自洽。
  • 规模保护：组合数超过 20 万时自动改为随机抽样，并在界面与报告中明确标注"抽样"。
  • 性能：预计算影响值表 IMP[源][目标][源状态][目标状态]，避免内层循环重复解析。
/* 判定核心（节选） */
for(let i=0;i<n && ok;i++){
  let mx=-1e9, pickv=0;
  for(let j=0;j<sizes[i];j++){
    let s=0;
    for(let k=0;k<n;k++){ if(k!==i) s+=IMP[k][i][idxOf[k]][j]; }
    if(j===idxOf[i]) pickv=s;
    if(s>mx) mx=s;
  }
  if(pickv<mx-1e-6) ok=false;   // 选定状态不是最高分 → 不自洽
}

它算得对不对——单独验证过

算法不能只靠"看起来对"。用一个独立测试脚本把平台代码加载起来跑：
· 构造 3 个描述符（各 3 个状态，共 27 种组合）
· 矩阵设定为「经济 ↔ 产业 +3 互相促进」「经济 ↔ 人口 −3 互相抑制」
· 运行结果：5 组自洽、22 组不自洽
· 自洽的 5 组全部满足「经济与产业同向、人口与经济增长反向」——与矩阵规则完全吻合

每次改动后都会重跑这个测试，避免改坏。

实际效果

平台里不再有编造的数字。检验结果给出：组合空间、实际检查数（全枚举还是抽样）、自洽情景数、不自洽组合数；每个自洽情景可展开，看它每个描述符的影响平衡明细（哪个状态拿多少分、最高的是哪个）。

4　影响关系图

解决什么问题

"它这还把描述符的 state 和另外一个描述符的 state 之间的影响强弱进行可视化，相当于知识图谱啊……所以说我觉得我们这个软件也应该加上这个功能。"

怎么实现

  • 纯 SVG 环形布局：描述符均匀排在圆周上，节点为自适应宽度的椭圆。
  • 连线用二次贝塞尔曲线；双向影响分别向两侧弯曲，避免 A→B 与 B→A 两条线重叠看不清。
  • 绿线＝促进、红线＝抑制；线宽与透明度随分值绝对值变化；箭头用两个不同的 marker 区分正负。
  • 悬停任一连线，显示这条判断的：源 → 目标、分值、语义（强烈促进／中度抑制…）、依据原文。
  • 与打分矩阵联动——改一格分值，图立即重绘。

实际效果

把打分矩阵从数字表变成能一眼看懂的图。这一屏也是与数据集侧工作的接缝处：目前节点与连线是描述符级的，等状态级证据链接进来后，每条连线点开就能显示"哪份政策文件的哪一条支持这个 +3"。

5　主被动图

解决什么问题

回答一个用户最先会问的问题：这个系统里，我该动哪个描述符？

怎么实现

  • 对每个描述符算两个数：主动和 ＝ 它指向其他描述符的影响绝对值之和；被动和 ＝ 其他描述符指向它的影响绝对值之和。
  • 散点图：横轴被动和、纵轴主动和，用两条平均值虚线分成四个象限。
  • 四象限对应四种角色：驱动者（影响别人多）、关键枢纽（两头都高）、结果型（被影响多）、惰性（两头都低）。

实际效果

图下直接点名主动和最高的三个描述符——它们是系统的"发动机"，动它们最容易带动全局；右下角的"结果型"则是政策发力后最先出现变化的地方。

6　情景表

解决什么问题

自洽情景可能有几十个，列成清单看不出它们之间的亲疏关系。

怎么实现

  • 列＝自洽情景，行＝描述符，单元格内容是该情景下该描述符取的状态。
  • 相邻情景里取同一状态的单元格自动合并（用 colspan），一眼看出哪些情景"是一伙的"。
  • 状态按索引着色；整块越大，说明该描述符在这些情景里越没有争议。

实际效果

把"几十个情景"变成一张可以扫视的表。

7　情景报告

解决什么问题

"一方面是可以给模型的配置情景设定提供一套，但同时也可以一键生成一个报告，或者一键生成一个情景的逻辑叙事……可以通过 API 接口给那些其他的系统去 input，也可以直接就面向我们那个 to C 用户。"

怎么实现

  • reportData() 把当前配置整理成结构化数据，buildReportHTML() 渲染成报告。
  • 报告结构（参照官方手册 6.3 节）：项目信息 → 描述符与状态 → 交叉影响判断明细（按强度排序）与影响平衡 → 情景检验结果 → 模型配置摘要 → 结论。
  • 两条出口：给人看——下载 HTML（自带内联样式，脱离平台也能独立打开）；给系统用——导出 JSON。

9　状态半定量化（取值区间）

解决什么问题

"高速／中速，这是一个很自然语言、很模糊的东西……可以让用户自己定义范围……这就实现了一个半定量。"

"标准也不是说只有一套标准。"

怎么实现

  • 区间数据：19 个描述符的 55 个状态各挂一组 [下限, 上限, 单位]——例如"高速＝5.0–7.0%""中速＝3.5–5.0%""低速＝0–3.5%"。预置值集中在 RANGE_PRESET 一处，便于整体替换成另一套标准。
  • 状态列表收口：原先多处直接读 d.s，用户一旦增删状态就会与界面脱节。现统一改走 ST(描述符名) 访问器，共 8 个调用点（检算、情景详情、情景表、报告、导出等），状态可增删改而不会算错。
  • 编辑交互：点状态右侧的区间标签即在原位展开编辑条——改上下限与单位、重命名状态、删除状态（仅自定义状态可删，且每个描述符至少保留一个）；每个描述符卡片底部另有"＋ 自定义状态"入口。
  • 同步：重命名或删除状态时同步更新已选状态清单 sel.desc[名].states，避免矩阵与报告里留下已不存在的状态名。
  • 区间依据分层（后补）：55 个状态的区间并非都同样可信，逐个标注证据强度——RANGE_EVID 分四类：政策目标（可直接对齐政策文件的定量目标）、需换算（有目标但口径不同，如森林覆盖率对碳汇量）、示例值（未找到对应目标）、外生输入（SSP 给定）。界面徽标可悬停看依据原文，报告里单列一栏。人工改过区间后自动降为「已改」，原依据不再自动适用——改了数还挂着政策依据，是最容易出问题的地方。
  • 衔接检查：rngIssues() 把各档按数值排序后检查是否存在重叠或空档，有问题直接在描述符卡片上提示。判据有意不依赖档位顺序——有些描述符（如单位产品能耗限额）数值越小反而意味着要求越严。

实际效果

区间不只在状态设置那一屏，而是贯穿全流程：打分侧栏里显示两端当前状态各落在什么范围，情景表每格下方标出该状态的区间，情景详情与情景报告同样带上——情景之间的差异因此不只在标签上，也落在数值范围上。又因为状态可增删、名称可改、区间可替换，不同研究可以采用各自的标准，不必锁死在平台预置的那一套。

10　多专家集成（分人打分、分歧裁定）

解决什么问题

"还得有一个吧……你现在有一个 agent 可以打分啊，就是人机协同啊……应该是让那个 agent 先填一版出来，然后有人来审核……这个审核可以有一个人来审核，两个人来审核，三个人来审核。"

"AI 可以给出一个，他说可以打 3 分、打 2 分也好，有个依据让人来（审）……"

"我打了一个这么一个点，就这一个点就可以是一个创新点。"

怎么实现

  • 矩阵不复制，只换引用：cim 直接就是"当前打分人那一份"的对象引用，切换人只换引用——这样任何一处改分都落在正确的那份矩阵上，不存在两套数据需要同步的问题。
  • 建立多份：buildEns() 按专家数生成 A / B / C 三份，第一位接管当前矩阵——因此可以先让 AI 预填一版、再"以当前为准分发"给其余专家作为起点，然后各人分头复核。
  • 比对：ensStat() 逐条比对各人取值，打分差 ≥ 2 判为分歧，其余归入一致；给出可比条目数、一致条数、分歧条数与一致率。
  • 合并规则：ensMerge() 把一致条目取共识值（多人取均值，置信度取各人中最高的，已审状态取交集）；分歧条目暂取中位数并标为低置信度、注明"待裁定"。
  • 裁定：arbit() 对某一条分歧项选定某位专家的取值，或 arbitAllMed() 一键全部取中位数；裁定结果写回主矩阵并把依据改成"原取值 a / b / c，经裁定取 x"，留痕可追溯。
  • 界面三处：校验方式屏（建立矩阵、说明规则）、打分屏顶部（打分人切换条 ＋ 实时一致率）、检验与导出屏（分歧明细表：每条列出各人取值与依据，旁边就是裁定按钮）。
  • 导出集成工作簿：exportEns() 输出 HTML——分歧明细 ＋ 合并后的完整矩阵，可发给专家讨论（对应德国软件 6.9 / 6.10 的 Ensemble 模式）。
/* 合并规则（节选） */
if(sp>=2 && 已裁定)  → {v:裁定值, conf:'高', why:'多专家分歧（原取值 …），经裁定取 …', rev:true}
else if(sp>=2)       → {v:中位数, conf:'低', why:'多专家分歧（…），暂取中位数，待裁定', rev:false}
else                 → {v:均值,   conf:各人最高, why:'多专家一致（…）', rev:各人是否都已审}

实际效果

导师说的"AI 先填一版、一到三个人审核"到这里形成了完整闭环：AI 预填 → 分人复核 → 自动比对分歧 → 逐条裁定 → 合并进检验。分歧项不是被平均掉，而是被挑出来交给具体的人做决定，并且每次裁定都留下原取值记录。

顺带修掉两个旧缺陷：① 保存 / 载入原先只存描述符与设置，不保存打分矩阵，一保存一载入分数就没了；② "清空重来"与"AI 预填"会用 cim={} 重建对象，在多人模式下会切断与专家矩阵的引用，改动落到一个游离对象上——现已改为清空内容、保留对象。

验证：test_ens.js 以 DOM 桩真跑，验九项——建立后第一位是否接管当前矩阵、切换人时引用是否跟着走、极差 ≥ 2 是否被识别为分歧、各份矩阵是否互不污染、合并是否分歧取中位数 / 一致取均值、裁定是否生效、清空与预填是否仍保持引用、退出多人模式是否正常。

11　情景地图（情景族聚类 / 状态分布热力图）

解决什么问题

"最后你无论怎么着要有一个图。"

"总得有个图，要不然别人认同不了你这个工作的价值。"

（翻德国软件时）他专门点了相似性聚类与热力图两块。

自洽情景往往不是一两个，而是几十上百个。看表能逐条核对，看不出整体格局。这一块补的是"看格局"的那只眼睛。

怎么实现

  • 情景相似度：两个情景之间，取值相同的描述符占全部描述符的比例。scenSim()
  • 聚类：层次聚类、平均连接（scenClusters()）。族内允许的差异随描述符数自适应——allow = max(1, round(m × 0.3))。这条不是可有可无的微调：若把阈值写死成一个相似度（如 0.7），描述符一少（比如只用 3 个描述符演示），0.7 就退化成"必须完全相同"，聚类形同虚设。
  • 族的定义：族内所有情景取值都相同的描述符才写进该族定义（familyDesc()）。于是族与族的差别＝这套假设体系下真正的分歧点；其余描述符无论怎么取都自洽，说明它们不是关键变量。
  • 布局：族中心均匀分布在圆周上，族内情景围绕族中心排布，各带配色与半透明底圈。确定性布局（不引入随机数）——同一份数据每次画出来都一样，便于汇报与留档比对。
  • 热力图：行是描述符、列是它的各档位，格子深浅＝在所有自洽情景里取这一档的比例。占比 ≥ 90% 的描述符会被自动点出——说明它被其他条件锁死，不是可自由选择的项。

if(m - best*m > allow) break;    // 平均相同数不足 allow 个，不再合并
// m = 描述符数，best = 待合并两族的平均相似度

实际效果

两张图回答两个不同的问题：聚类图答"这些自洽情景分成几派、派与派差在哪"，热力图答"每个描述符在这套体系里倾向取哪一档"。情景表给人逐条核对的依据，情景地图给人整体判断的依据——"别人认同不了你这个工作的价值"，指的正是后者。

12　情景筛选（按条件反查情景）

解决什么问题

自洽情景往往几十上百个——组合空间越大，这个数就越大（19 个描述符、55 个状态，全组合 3¹⁰×2² ≈ 23.6 万）。情景表一次只显示前 30 列、情景地图只布局前 60 个，光靠翻看不解决问题。用户真正想问的是——"如果要求某某，还剩哪些自洽情景？"

德国软件在 6.7 节内置了三种形式化筛选程序。这一版取其中最实用的一个方向：按描述符的取值反查。

怎么实现

  • 条件集合：filt = {描述符名: 状态索引}；界面上每个已选描述符一行，下拉选"不限"或某一档。
  • 计算：filtList() 对自洽情景列表做过滤，多条件取交集（AND）；没有条件时直接返回全量。
  • 边际命中：每个条件旁显示"只加这一个条件会命中多少、占多少"。这一列让用户一眼看出哪个条件是紧的——命中很少，说明这条要求约束力强。
  • 零命中的处理：若组合起来命中 0，界面明确写出"这组要求在自洽情景里不存在——这些状态不可能同时成立。这本身就是一条结论"。这不是装饰：CIB 的价值恰恰在于能告诉你哪些设想组合站不住，而不只是列出可行的组合。
  • 筛选只作用于展示层：情景表、情景族聚类图、状态分布热力图三处改用 filtList()，并在各自说明里注明"已按筛选条件"。检验结果本身不变——全量自洽情景数照原样显示，避免把"筛选后的子集"误当成"自洽情景的总数"。
/* 过滤（节选） */
function filtList(){
  if(!cimResult) return [];
  if(!filtN()) return cimResult.consistent;          // 无条件＝全量
  const ds=cimResult.ds;
  return cimResult.consistent.filter(cb=>ds.every((d,i)=>filt[d]===undefined||cb[i]===filt[d]));
}

实际效果

这一块把平台从"列出所有可能的未来"推进到"按设想反查未来"：用户可以问"如果坚持非化石能源高占比，哪些自洽情景还成立""如果钢铁仍以长流程为主，会连带锁死哪些描述符"——答案立刻反映在表和图上。

验证：test_filt.js 验六组——无条件时等于全量、单条件命中数正确、清除条件后恢复、多条件取交集、互斥条件命中 0 并给出提示、筛选后三处展示是否都跟随。

13　状态级精判（把打分真正打到状态对）

解决什么问题

CIB 的原始设定是判断状态对之间的影响——19 个描述符、55 个状态意味着 55×55 ≈ 2970 个格子。而此前的做法是在描述符级（19×19）打分，再用"两端状态高低位置"把分值展开到状态级。

这个展开是一个假设，不是一次判断。它的问题很具体：如果"碳价 → 钢铁工艺"记为 +2，展开规则会认为"碳价高位 × 短流程"与"碳价低位 × 长流程"同样成立；但现实里可能恰恰相反——碳价很高时，长流程不是"被促进"，而是"被淘汰"，两者并非对称。这类非对称关系，展开规则表达不出来。

但反过来，强迫用户填满 2970 格也不现实。所以这一版的取舍是：整体倾向仍作默认，每条判断可展开到状态对逐格精判。

怎么实现

  • 数据结构：每条判断加 st 字段，键为 源状态索引_目标状态索引，值为 −3…+3。没有 st 就是没精判过。
  • 取值优先级：impactVal() 先查 st，查到就用；查不到才退回默认展开。也就是精判永远压过默认。
  • 默认展开单独抽出来：expandV() 一个函数表达全部展开规则，并在代码注释与界面上都写明它是"兜底假设"。把"假设"和"判断"分开命名，是这一步的关键——否则半年后没人说得清哪个数是人填的。
  • 界面：打分侧栏下半部分是一张状态下拉矩阵。未改的格子显示 默认(+2)，改了的标蓝加粗，并在标题旁计数"已改 N 格"；一键可全部恢复默认。矩阵格子的右下角有小圆点，标出哪些判断含精判，一眼看得到。
  • 统计与报告：统计栏显示"状态级精判 N 条 / M 格"；报告里如实写出精判条数与其余为默认展开——不把两者混为一谈。
/* 取值优先级（节选） */
function impactVal(fd,fi,td,ti){
  const r=cim[fd+'>'+td];
  if(!r) return 0;
  if(r.st){
    const ov=r.st[fi+'_'+ti];
    if(typeof ov==='number') return ov;      // 人工精判优先
  }
  return expandV(r.v, ST(fd).length, fi, ST(td).length, ti);   // 否则退回默认展开
}

实际效果

做法上是一个折中，但把最关键的性质保住了：凡是用户填过的格子，都出自真实判断；没填的格子，界面上明确标着"默认"。 于是汇报时可以说清楚哪部分是人的判断、哪部分是平台的假设，而不是笼统地说"我们的打分是状态级的"。

验证：test_stlvl.js 验六组——描述符级为 0 时展开值全为 0、改成 +2 后 3×3 展开矩阵符合对称规则（对角 +2、反对角 −2）、精判覆盖生效且未精判格子不受影响、清除后恢复默认、侧栏渲染出 9 个下拉与角标、报告数据带出精判条数。

其中最关键的一条：构造一组"全部打 0（此时 27 个组合全自洽）"的数据，再对一条判断加状态级精判，自洽情景数由 27 变为 21——证明精判确实进入了检算，而不只是显示层的一个数字。

14　跨层一致性（纵向检验）

先说明一件事

这一块与前面各节不同：它的规则没有外部依据，是我们自己定的。

面谈录音 553 段通检，"跨层 / 层级 / 汇总 / 加总 / 边界"等词只有零星几处，没有一处是导师对跨层约束的定义。唯一相关的是我演示平台时自己说的一句："上下联动约束，就是下级的⋯总和必须要等于上级，也就是口径需要一致。" 导师当时没有接这个话题，转而讲了半定量。

而"分解汇总 / 口径一致 / 边界不越"这三条，只存在于平台 v1.0 自己的界面文案里，是早期拟的表述。所以本节的所有规则都应读作设计假设，需要当面与导师确认。

解决什么问题

多尺度的实质不是"界面上能勾三个层级"，而是同一套假设在三个尺度上必须自洽。国家级定了"加速服务化"，某个市却定"转型滞后"——这不是两种观点，这是同一个假设内部的矛盾。

但要注意分寸：上级是边界条件，不是标准答案。省级可以在国家级给定的空间里选"相同"或"更保守一档"，不能反向。约束是允许范围，不是必须相同。

怎么实现

  • 数据结构：xlSel[描述符名] = { nation:档位, prov:档位, city:档位 }，与 CIB 矩阵彼此独立。
  • 检查对象：只查同一个描述符在相邻层级之间的关系（nation→prov、prov→city），不跨描述符。
  • 判据：档位差 0＝完全一致，1＝有梯度（允许），2＝方向相反（冲突）。这条判据的关键在于承认"梯度"是正常的——省级本就该比国家级保守或激进一档，把它判成矛盾是错的。
  • 修复：xlAlign() 把冲突格的下级调到与上级相邻的档位，不强制同档。
  • 界面：描述符 × 层级 的取值表，冲突格标红并逐条文字说明（"省级取「高位并扩围」，市级却取「低位维持」——方向相反，跨 2 档"）。每格下方带该状态的取值区间，让人同时看到量级。

三处取舍，需要说明理由

  • 为什么不把跨层约束并入 CIB 的组合枚举？ 因为算不动。19 个描述符 × 3 层 = 57 个节点，全组合 3⁵⁷，任何枚举或抽样都失去意义。所以这一版把纵向相容做成独立校验：横向（CIB）与纵向（跨层）是两个正交的检验，各自通过，合起来才算这套假设站得住。要真正联合求解，得另做分层剪枝或局部搜索。
  • 为什么不做数值加总校验？ 因为层结构不同构。北京、天津、河北是三个平级单位，而市级只覆盖河北的 11 个地级市——"三省之和＝全国"在京津冀语境下根本不成立（京津冀只是全国的一部分），"河北各市之和＝河北"才是成立的。前提没厘清之前做加总，只会做出一个看起来严谨、实际错误的东西。
  • 为什么"口径一致"没有做成检验？ 因为它是前置条件，不是检验对象。如果"人口"在国家层面含常住、在省级只含户籍，"三省加总＝全国"这个检验本身就是错的。机器判断不了两处"人口"是不是同一定义，这一条必须在建库阶段解决。

实际效果

平台现在能回答一个德国软件回答不了的问题："这套跨尺度的假设，上下对得上吗？" 用户可以逐层指定取值，冲突会立刻标出并给出修复建议。虽然规则是自研的，但它是可解释、可争论的——这正是下一步要拿去和导师讨论的东西。

15　数值锚定（让状态区间参与检算）

解决什么问题

第 9 节把定性标签落成了取值区间，但那些区间此前只起说明作用——一致性检验只问"选定状态是否为影响平衡的最高分"，完全不看这个状态的数值前提是否现实。也就是说，一个逻辑上完全自洽的情景，可能建立在一组早已被现实否掉的数值假设上。

这一节补的是数值层面的可行性约束：如果已知某个量现实落在 4.5~5.0，那么取"5.0~7.0"这一档的状态就不该再进检验——不必等算完再人工挑出来。

怎么实现

  • 锚定输入：anchors[描述符名] = {lo, hi}，界面上每个已选描述符一行，接受单值 4.8 或区间 4.5~5.0。
  • 排除判据：状态区间 [lo,hi] 与锚定区间 完全不相交才排除。部分重叠的保留——它仍可能与已知值相容，一刀切掉太武断。
  • 无区间不排除：某个状态若还没配区间，不因锚定被否掉。缺少数值依据时，不能反过来把它当作"数值上不可能"。
  • 在收窄后的空间上枚举：这一点是关键。实现改成了混合基数枚举——先把每个描述符可用状态集算出来，再在其乘积空间上取组合，而不是"全空间枚举 + 逐个过滤"。后者在抽样模式下几乎全是废样本（例如 27 种里只剩 9 种，命中率 1/3；描述符一多就会低到不可用）。
  • 透明度：检算结果与情景报告都标出「原始组合空间 → 锚定后」，并给出被排除的组合数；界面上每个描述符旁显示"可用 k / n"。
  • 无解即拒算：某描述符被锚定到没有任何可用状态时，直接提示并中止，不产生一个空结果让人误读成"没有自洽情景"。

17　逐层求解（跨层约束真正进入枚举）

解决什么问题

第 14 节的「跨层一致性」是算完再查：各层各自求解，再用档位差比对。它有两个不足：

  • 约束来得太晚：下级那份「快速清洁化」算完才发现与上级不相容，白算一遍；
  • 只查档位、不查数值：档位差 1 就算通过，但「上级 21–28%」与「下级 30–40%」明明一个数都不重叠，档位却可能只差一档。

逐层求解把约束挪到枚举之前：上级的取值先转成区间，下级与它不相交的状态直接不进搜索空间。

怎么实现

  • 取值 → 区间：rangeOf(描述符, 层级) 按层级取区间（第 16 节的分层数据）。上级某一情景里取了「目标节奏」，就取它在上级那一层的区间（如区域级 20–30%）。
  • 区间 → 允许集：allowUnder() 把上级区间与下级每个状态的区间做相交判断，不相交的排除。上级 20–30% 对北京「快速清洁化 28–36%」相交（28–30）→ 保留；对「推进迟缓 14–21%」也相交（20–21）→ 保留；但上级「推进迟缓 10–20%」对北京「快速清洁化 28–36%」完全不相交 → 排除。
  • 逐层串起来：runLayered() 从第一个非国家级层级开始，解完一层就把每个自洽情景作为下一层的约束，依次往下。国家级是给定层（政策目标），不参与枚举。
  • 无解单独计数：某个上级情景若让下级一个状态都不剩，该分支记入 dead 并跳过。这个数字本身是结论——"区域级按加速服务化走，河北没有实现空间"，比强行算出一组矛盾的情景有用。
  • 路径可追溯：每个最终组合带完整 path（区域情景 → 省情景 → 市情景），界面上直接摊开每一层的取值。
/* 相交判断（节选） */
if(c.hi < pR.lo || c.lo > pR.hi) continue;   // 下级区间与上级区间完全不重叠 → 该状态不进枚举

计算量

全枚举 19 个描述符 × 3 层约为 3⁵⁷，不可能。逐层求解是 M × 3^k（M＝上级自洽情景数，k＝每层描述符数）：

做法量级说明
一次性全枚举3⁵⁷不可行
逐层求解M × 3^kk=6、M=10 时约 7 千次判断；且上级区间会进一步裁掉下级状态，实际更少

实际效果

测试里用两个描述符、三层各 3 档跑通：区域级 9 组自洽 → 省级 81 组（9 个上级 × 9）→ 市级 600 组（截断，实际 729）。每条最终组合都能追溯到它在三层各自取了什么。

更关键的是两个反例，说明这个方法真的在传导而不是摆设：

  • 区域级取「加速服务化」（72–80%），河北无解——河北最高档只到 66%。河北到不了 72%，这不是河北不努力，是这套上级设想在河北没有实现空间。
  • 区域级取「稳步演进」（65–72%），河北只能取「加速服务化」（58–66%）——两者在 65–66 有一段重叠。同样叫「加速服务化」，河北的 58–66% 对区域级的 65–72% 来说其实是"跟上"，而不是"冒进"。

验证：test_layered.js 验五项——上级三种取值下北京可用状态是否正确、上级「加速服务化」时河北无解、单层求解结果与普通 CIB 检算完全一致（9 组）、三层路径完整、无省级口径时退化为单层且路径仍带父层。

18　影响路径分析（间接传导链）

解决什么问题

矩阵里两个描述符之间没有打分，很容易被理解成「互不影响」。但影响是可以绕一层的：煤炭消费结构不改，电力部门就难以清洁化；电力不清洁，终端电气化反而增排。三者两两之间也许只有一段直接判断，合起来却是一条完整的传导链。

这一块补的是「为什么两个看起来无关的描述符会互相影响」。它也直接对应多尺度：国家目标 → 省域结构 → 市级排放，本质就是一条路径。

怎么实现

  • 搜索：findPaths(from,to,maxSeg) 在已选描述符上做深度优先遍历，只走非零影响的边，不重复经过同一节点，收集全部 2—3 段（最多 2 个中间环节）的有向链。
  • 强度：一条链有多强，取决于它最弱的那一段——+3 接 +1，整体只按 +1 算。不用连乘也不用求和：连乘会因符号与量级迅速失真，求和会把一条「中间被卡死」的链算得比实际强。
  • 方向：看负号个数，偶数个为净促进、奇数个为净抑制。
  • 排序：先按最弱环节的绝对值降序，同强度时短链优先。
  • 隐性关联：hiddenLinks() 扫全部配对，列出直接判断为 0、却存在间接通路的那些——它们提示矩阵里可能漏了一条关系。点击某一行即可把起点终点切过去细看。
  • 提示：若直接判断已填 0 但存在间接链，界面明确写出「这两个描述符其实有关系，只是绕了一层」，建议回到矩阵补直接判断，或在依据里注明「经某某间接影响」。
/* 强度与方向（节选） */
const signs  = p.vals.filter(v => v < 0).length;          // 负号个数
const minAbs = p.vals.reduce((a,v) => Math.min(a, Math.abs(v)), 99);
return {dir: signs % 2 ? 'neg' : 'pos', minAbs};

一个实现上的坑（值得记）

第一版把段数判据写成 if(path.length >= maxSeg) return;，结果三段链永远找不到——走到第二个中间节点时段数已到上限，程序在「判断是否到达终点」之前就返回了。正确判据按段数（节点数减一）而不是节点数：seg = path.length - 1; if(seg > maxSeg) return;。测试里专门留了一条「A→B→C→D 应找到 1 条 3 段链」，就是用来卡这个的。

另一条判据：到达终点后立即返回，不再延伸——否则 A→B→C→B 这类绕回起点的链会被重复计入。

实际效果

选定「一次能源结构 → 终端电气化率」这类起终点，界面会列出所有 2—3 段通路，每条都标出净促进 / 净抑制与瓶颈强度。如果这两格之间本来填的是 0，而下面又挂着两条链，就等于被指出来：矩阵漏了一条关系。

该模块与「影响关系图」互补：关系图看直接边的全局格局，路径分析看两点之间的传导；前者回答「谁最中心」，后者回答「为什么会传过去」。

19　影响谱（外部冲击会挤掉哪些可能）

解决什么问题

情景集本身是一张「哪些组合站得住」的地图。决策者更常问的却是另一种问题：如果某件事被强行实现——比如 GDP 增速被压到低位、或某条硬指标必须达成——地图上还剩下什么？

德国软件把这类分析叫 Influence profile：逐个把某个状态「钉死」，重算情景集，再与基准对比。本版实现的是其中的定性版——只回答「有没有」和「变了没有」，不统计频率变化。

怎么实现

  • 复用同一套枚举：把一致性检验的内核抽成 enumCore(ds, force, capN)。传 force={pos,idx} 时，第 pos 个描述符的可选集合被收成只有一个状态——相当于外部力量把它钉死了。
  • 基准与对照：先算不强制时的自洽集，记下每个状态是否在某个自洽情景里出现过（presence，而不是只看情景条数）；再对每个状态逐个强制、重算，比对两次的 presence。
  • 两种结果：被挤掉（基准里有、强制后没有）；整行为 0（该状态下没有任何自洽情景）。后者是最强的结论——这条冲击与当前全部判断不相容。
  • 预算控制：状态多时逐次强制会变成几十上百次重算。按状态总数给每次强制分配抽样量，总量控制在约 40 万个组合；有抽样时在界面注明，并说明「方向可靠、具体条数会浮动」。
  • 明细：点任一行，展开该冲击后被挤掉的具体状态清单（哪个描述符的哪一档）。
/* 强制某个状态（节选） */
const allowed = ds.map(d => ancAllowed(d));
if(force) allowed[force.pos] = [force.idx];      // 把该描述符收成唯一状态
const dead = allowed.findIndex(a => !a.length);
if(dead >= 0) return {dead: dead};                // 被锚定清空

一处必须讲清的方法边界

本版把「强制」实现为硬约束。这在数学上意味着一个性质：强制后的自洽集必然是基准集的子集——因为判定规则没变，只是可选的组合变少了。所以本版只会出现「被挤掉」，不会出现「被打开」。

而德国软件的手册里明确有 [+] 标记（原本不存在、强制后出现）。它之所以能做到，是因为它把外部冲击当作会改写矩阵的影响来处理（相当于新增一条外部影响，改变了各状态的影响平衡），而不只是限制组合空间。那是另一种建模，需要额外定义「这条冲击如何影响其他变量」——本版没有采用，界面上也如实标注了这一点。

这是有意为之：宁可少一个标记，也不要做出一个看起来有、实际靠不住的结论。 如果将来要补这种模式，正确做法是让用户为冲击填写影响向量（对哪些描述符、多强），而不是从「强制一个状态」里推出连带的矩阵变化。

实际效果

它回答的是「哪些门会被关掉」：某个状态被钉死后，哪些原本可能的搭配不再成立；哪些状态被钉死后整个情景集清空。对政策讨论来说，后一类往往比前一类更有信息量——它直接说明「这件事和目前这套判断体系不相容」，要么放弃它，要么修正判断。

与相邻模块的分工：情景筛选是「按我的要求过滤已有情景」；数值锚定是「按已知数值排除状态」；影响谱是「假设某个状态被外部力量钉死，整套情景集会怎么变」——三者的作用点分别是展示、检算前、检算后重算。

验证：test_prof.js 验五项——① 全零矩阵基准 27 组、强制任一状态后 9 组、无状态被挤掉；② 让某个状态永远不是最优时，强制它得到空集（且另一同类的状态同样为空，共 2 行）；③ 设计一条只在特定取值下成立的边，强制该状态后另外两个状态被挤出（21 组 → 3 组）；④ 渲染含表格、基准行、空集提示与硬约束说明；⑤ 描述符不足时返回错误而非崩溃。

另外做了一次回归确认：抽出 enumCore 之后，CIB 算法测试仍是「3 描述符 27 组合 → 5 组自洽」，数值锚定测试仍是「27 → 9」，说明这次重构没有改变任何判定语义。

20　相关性分析（哪些状态总是绑在一起）

解决什么问题

情景表能看出「有哪几十种搭配」，但看不出「哪些搭配其实是同一件事的两种说法」。相关性分析回答的是后者：某些状态是不是总一起出现？——如果「经济高速」和「产业结构加速服务化」在几乎所有自洽情景里都同进同出，那它们在讨论中其实是一个判断，不该当成两个独立的自由度。

怎么实现

  • 系数选择：状态只有「出现 / 不出现」两种取值，因此用 Pearson φ 系数（等价于两个二值变量的皮尔逊相关）。手册 6.13 用的也是这个公式，结果以整数百分比呈现。
  • 统计口径：以全部自洽情景为样本，而不是情景表里展示的前 200 条——展示是截断的，用来算统计量会失真。为此给枚举内核加了 keepAll 参数（上限 8000 条，超出时界面注明）。
  • 只算跨描述符配对：这是本版一个必要的取舍。同一描述符的不同状态天然互斥，φ 恒为 −100%，若一并计入，「强关联」列表会被这些构造性结果占满，真正有价值的信息被淹掉。
  • 无区分度的状态不计：从不出现、或每组情景里都出现的状态，其方差为零，φ 无从计算——按手册做法留空。
  • 小样本警示：情景数 < 20 时界面直接提示「系数可能不稳定」。这条不是客套——手册原话是 correlation coefficients of small scenario sets may lead to artificial results。
  • 两种视图：强关联列表（|φ| ≥ 80%，带条形和正负配色）看全局捆绑关系；单个状态的关联谱看某个状态跟谁最亲近（对应手册的 correlation profile）。
/* φ 系数（等价于二值变量的皮尔逊相关） */
nAB = #(A 与 B 同现)      n10 = nA − nAB      n01 = nB − nAB
n00 = S − nA − nB + nAB
phi = (nAB·n00 − n10·n01) / sqrt(nA·(S−nA)·nB·(S−nB))

两处必须说清的边界

① φ 不是因果。它只说「是否同进同出」。两个状态高度相关，可能是因为一个推动另一个，也可能因为同受第三个变量驱动（例如都受「碳价」影响）——先后与因果要看交叉影响矩阵和影响路径。界面底部写明了这一点。

② 相关会随判断变。换一套打分、或加一个锚定，情景集就变了，系数也随之变。它描述的是「在当前这套判断下这些状态怎么搭」，不是京津冀的客观属性。汇报时应说明是在哪个情景集上算的。

实际效果

典型读法：若「高速增长」与「加速服务化」的 φ 达到 +90%，说明在这套判断下二者几乎不可分——讨论时不该把它们当成两个可以独立选择的旋钮；若某个描述符的若干状态与谁都只有弱相关，说明它在这套体系里相对独立，是个可以单独发力的抓手。

验证：test_corr.js 七项，其中两处用手算对照： ① 设计一条只在 A 取第 1 档时成立的边（21 组情景），手算 φ(A1,B1)=+47%、φ(A1,B2)=−26%，程序输出一致； ② 构造完全耦合的三档映射（9 组情景），φ(A1,B1)=+100%、φ(A2,B3)=+100%、φ(A1,B3)=−50%，与手算一致。 另验：同描述符配对不出现、全零矩阵下所有 φ 均为 0、小样本警示与关联谱渲染、描述符不足时返回错误。

21　演示模式（七章，只读）

解决什么问题

平台是给人「操作」的，汇报是给人「听」的。同一套内容，前者需要按钮、下拉、表单，后者需要大字、少项、按预定顺序讲。若不分开，汇报时就得一边找控件一边讲，容易翻错页、点错格子。

德国软件把这层单独做成一章（第 8 章 The Presenter），定位写得很清楚：把 CIB 分析的数据和结果，按预先排好的顺序讲给一屋子人听；全屏、只用鼠标点、所有显示元素锁定输入。

怎么实现

  • 独立全屏层：顶栏一个入口，打开后覆盖整个页面（position:fixed），左侧章节导航、底部翻页、Esc 退出；不改动主流程任何状态。
  • 七章，按 CIB 演示的常规顺序：开场 → 描述符与状态 → 政策库与映射 → 交叉影响 → 自洽情景 → 钻进一个情景 → 跨层一致性。
  • 按条件禁用章节：没有自洽情景时，「自洽情景」「钻进一个情景」灰掉；描述符不足两个时，「交叉影响」灰掉。翻页会自动跳过这些章节——避免把空页面投到大屏上。
  • 只读：七章里没有任何输入控件，全部由当前状态渲染而成。演示时点不到、也改不坏。
  • 超 50 组提示：自洽情景超过 50 组时，情景页顶部给出提示，建议先在主流程的「情景筛选」里收到 50 组以内。这条来自手册的经验判断——一屋子人讨论 50 组以上管不过来。
  • 键盘：→ / 空格 / PageDown 下一页，← / PageUp 上一页，Esc 退出；同时保留鼠标按钮，触屏也适用。

两章是我们独有的

「政策库与映射」——德国软件从描述符开始（第 2 章就是 Descriptors），它没有「政策文本 → 模型变量」这一层。我们把它放在第三章，等于在讲 CIB 之前先交代上游是怎么来的。

「跨层一致性」——德国软件只有单层级，压根不存在这个问题。这一章放在最后，正好回答「多尺度到底多在哪」。

换句话说：六章是学它的，两章是我们的。（开场与政策库算两页，故共七章。）

实际效果

汇报时只需按顺序翻页，讲完一章按一下；鼠标不用找按钮，屏幕上看不到任何设置项。若某一章暂时没有内容（比如还没算情景），它会自动从翻页序列里消失，不会出现「这一页是空的，我们跳过」这种尴尬。

验证：test_pres.js 验十项——章节数与顺序、三种状态下各章可用性、翻页是否跳过不可用章节、导航中禁用按钮数、七章各自渲染的关键内容（开场三要点、描述符表含区间、政策库含 106 条与「不在口径内」、矩阵含正负分与低置信统计、情景页超 50 组告警且 ≤50 时不告警、单情景页含影响平衡与 ▲、跨层页含四层表头并检出「相差 2 档」冲突）、退出后遮罩关闭。

22　政策依据接入（文件名、口径、数据侧实证）

解决什么问题

政策库里每条路径都指着一两个描述符，但此前只有结论、没有出处：为什么「节能技术改造补贴」对应「工业节能改造强度」，界面上只有一句模型侧写的理由，看不到政策本身的证据。

而数据集的「工具总览」表里其实有：法律文件名称（409 条全覆盖）、具体口径（含定量目标的原文摘要）、对应描述符（33 条已填）。这些此前只存在于 Excel 里，平台上看不到。

怎么实现

  • 聚合而非手抄：脚本读数据集 409 条工具，按「路径」聚合，得到 58 条路径的证据记录：工具数、法律文件（最多 2 份、各截 44 字）、定量口径（最多 1 条、截 120 字）、数据侧实证描述符（最多 3 个）、涉及地区（最多 3 个）。生成 POLICY_EVID 数据对象，不手敲，避免与数据集脱节。
  • 界面呈现：政策库点任一路径，侧栏顶部出现「政策依据（数据集 · 工具总览）」区块——工具级记录数、涉及地区、书名号文件名、口径引文。
  • 两侧比对：把数据侧已填的描述符与模型侧映射逐条对照，给出三类结果——一致、模型侧另有（数据侧尚未建立）、数据侧另有（可能是绕一层的映射，也可能是口径差异）。
  • 没有记录的照实说：58 / 106 条路径有工具级记录，其余 48 条在数据集中尚无条目，区块直接写明「映射只能靠模型侧推断，置信度按中/低处理」。
  • 列表与统计：有记录的路径在列表里带一个「证」字标记；政策库统计条新增「有工具级记录 57 条」「含定量口径 30 条」。

一处必须讲清的边界

区块底部写着一句话：文件名与口径能证明「这条政策存在」，不能单独证明映射关系成立。

这两件事必须分开。数据集告诉你「北京有一份《碳排放权交易管理办法》，口径是对重点排放单位实行配额管理」；但「它对应到本模型的哪个变量」仍是模型侧依据「模型要什么 input」倒推出来的判断。把前者当成后者的证据，是这类工作最常见的自欺。

所以本版的做法是：证据列在一边，判断列在另一边，两者并置供人核对，而不是把文件名当成映射的授权书。

实际效果

以「排放交易体系（ETS）」为例，侧栏会显示：工具级记录 2 项、涉及北京 / 天津、《北京市碳排放权交易管理办法》《天津市碳排放权交易管理暂行办法》，以及一段口径引文；下面才是我方映射「碳价水平与碳市场覆盖（高）」。用户能一眼看出这条判断有没有政策实体支撑。

对「生态系统服务付费」这类已有实证的路径，还能直接看到数据侧填的描述符与我方是否一致——这就是导师说的「评分依据透明化」在政策库这一层的落地。

验证：test_pevid.js 七项——58 条证据、57 条能对上政策库名称、字段形状无异常、已知/未知路径查询、依据区块渲染（工具数/文件名/口径/边界说明）、有实证路径显示比对、无记录路径显示「尚无工具级记录」、统计条与列表「证」标记数量。

23　稳健性检验（判断改一档，结论还站得住吗）

解决什么问题

一致性检验的输入是人给的 −3 到 +3。审稿人一定会问：这些打分如果在合理范围内晃一下，自洽情景还站得住吗？哪些结论是骨架、哪些是碰巧？这一问题导师在面谈里反复出现过——「AI 打分、人来审核」的前提就是知道该把人审的力气花在哪。

怎么实现

  • 扰动重算（蒙特卡洛）：把每条已填判断按置信度随机改 1 档——低置信度改动的概率 0.5、中 0.25、高 0.08——同时重算整轮，默认 30 轮（可选 10 / 30 / 60）。统计每个状态在扰动后的出现率，≥90% 判「稳健」、50%—90% 判「敏感」、<50% 判「脆弱」。
  • 固定组合集：基准与每一轮扰动都评估同一批组合（全枚举或固定种子抽样 2000 个）。只有组合不变，才能回答「同一条情景在判断改动后还自不自洽」，而不是比较两个毫不相干的集合。
  • 单格翻转：逐条把某格改 ±1，统计基准自洽集（前 80 个）里有多少条被推翻。翻掉比例最高的 10 条列成表——这就是「最该先找人复核的判断」。人审的力气应该按这张表分配，而不是平均撒。
  • 过期提示：检验结果带一份矩阵指纹，打分再动过就提示「数字已对不上当前判断，建议重跑」。
  • 计算内核：单独实现 buildIMP（按给定矩阵展开状态级影响值）与 evalCombo（判单条组合自洽），判据与主检算 enumCore 完全同一条；测试里用全枚举比对过两条路径逐格一致。

边界（必须讲清）

结果不是概率。出现率 90% 不读成「这个情景有 90% 的可能发生」——它只衡量「判断晃动会不会改变结论」。CIB 方法本身不给概率，这里也不给。扰动幅度固定为 ±1 档：更大幅度的改动属于「换一套判断」而不是「同一判断的误差」。空间过大时为抽样近似（界面已标注）。

验证：test_robust.js 六项——evalCombo 全枚举与 enumCore 计数一致（27 组合逐格比对）、无打分报错、扰动轮次与状态行数、出现率落在 [0,1]、同种子确定性（两次结果序列完全相同）、打分改动后的过期提示、轮次钳制（999→100、2→5）。

24　描述符框架导入导出（算法通用、底料本地）

解决什么问题

导师的原话是「要通用工具，但也要落地」（录音第 65、345 段）。此前描述符树是写死在代码里的 19 个变量，「通用」停留在定位表述上。这一块把变量结构整体抽成可导入导出的 JSON：换一套行业或区域，同一套流程照跑；落地靠本地的数据与判断，通用性靠这一层。

怎么实现

  • JSON 结构：descriptors 数组，每项含名称、类型（输入型 / 参数型 / 结果型）、状态数组（≥2 个）、可选数值区间、界面分组。区间随框架一起走，导出再导入不丢。
  • 导入校验：非 JSON、不足 2 个描述符、状态少于 2 个、类型非法、重名——逐一当场报错，不带病运行。
  • 切换即清场：换框架等于换了一套变量，旧的选择、打分、锚定、全部分析结果一并清空，不留半套旧状态混进新框架。
  • 示例框架：内置「城市客运交通」5 描述符（含区间与翻译依据），一键载入，用于当场演示「同一套算法换一套变量照样跑」。
  • 随时可回：原框架首次切换前自动存底，「恢复京津冀框架」一键回去。

边界

导入的 JSON 只带变量结构（描述符、状态、区间），不带判断——换框架后打分必须重做，这是方法决定的，不是没做完。政策库映射不随框架走：新框架的描述符在政策库中覆盖数为 0，属正常现象，界面已如实显示。

验证：test_fw.js 十七项——五类非法输入逐一拒绝、合法导入后描述符 / 分组 / 选择 / 打分 / 结果 / 区间逐项核对、导出往返、恢复原框架、示例框架载入。

26　逐层求解规模化（19 个描述符三层可跑完）

解决什么问题

逐层求解此前只跑得动中等规模。旧内核让每个上级情景各枚举一遍下级空间——600 个上级 × 每组 20 万次评估，19 个描述符全开时（全空间约 5.2 亿种）根本跑不完，这正是「下一步计划」里挂着的规模化缺口。

怎么实现

  • 关键观察：判与筛分离。一条组合是否自洽只取决于它自己（各描述符取值 + 影响矩阵），与上级约束无关——上级约束只负责「筛」，不参与「判」。所以整层只判一遍（共享预算 25 万次评估：小空间精确枚举，大空间固定种子抽样），再把自洽组合按各组的允许集筛选，而不是每组重算。
  • 影响值预计算：整层共用一份状态级影响值表，不再逐组合反复查矩阵——旧实现的每次取值都带字符串拼接，这一步是最大的常数级浪费。
  • 归桶索引：自洽组合按前三维取值建桶，每个上级组只在自己允许的桶里逐条核对其余维，避免「全量 × 全组」的两两比对。
  • 蓄水池抽样：自洽组合超过 8 万条时等概率替换，避免枚举字典序带来的偏置。
  • 分层异步推进：每层算完刷新一次进度提示，浏览器不假死。

顺带修掉的一个旧缺陷

链式层级求解时，上级组的 scope / cb 挂在本组 path 的末节，旧代码读的却是顶层字段——恒为空，等于上级约束从未真正传进下级求解。旧测试恰好用全零矩阵（每条组合都自洽），约束传不传结果一样，于是被掩盖。修复后下级结果真正被上级收窄：同样的测试数据，省级从 81 组降到 49 组、市级从数百组收敛到 289 组。「上级定了目标节奏，下级快速清洁化不该再出现」这件事，从修复起才是真的。

边界

组合空间超过 25 万的层为固定种子抽样，界面已标注「抽样」，自洽组合数是下限而非精确值；小空间层仍为精确枚举。上级组列表本身有 600 组的展示上限。数值加总校验仍未做（层级树成员不完整）。

验证与实测：test_layered.js 扩到七组——新增中等规模（4 描述符精确枚举）与全量检算逐格一致、19 描述符抽样解逐条复检自洽且全部落在上级允许集内。另以 19 描述符基准实测：强耦合矩阵 0.85 秒 / 层，稀疏矩阵三层共 2.6 秒。

27　映射补证（联网核实政策原文，置信度动态更新）

解决什么问题

政策库里标"中 / 低"置信度的映射此前只有一句模型侧推断理由，没有政策实体支撑——这是边界表里挂着的欠账。补证不是把理由重写一遍，而是拿政策原文来对质：找到文件、文号、关键条款，再决定这条判断是站得住还是该降级。

怎么实现

  • 按描述符聚类核实，不逐条硬搜：把 45 条"中"置信度映射按目标描述符聚成约 10 组（新能源汽车、建筑能效、能耗限额、碳价、本地可再生、区域互济、产业结构……），每组找到 1—2 份权威政策原文，组内条目共享依据。本次核实到的文件包括：发改价格〔2023〕1501 号（煤电容量电价）、工信部等五部门令第 64 号（双积分修订）、财税〔2018〕74 号（车船税）、GB 55015-2021（建筑节能通用规范，全文强制）、发改产业〔2023〕723 号（工业能效标杆/基准水平）、生态环境部碳市场扩围方案（钢铁水泥铝冶炼）、发改委令第 7 号（产业结构调整指导目录 2024 年本）、发改能源〔2019〕807 号（可再生电力消纳保障机制）、国务院令第 779 号（生态保护补偿条例）、财政部等 2023 年第 10 号公告（新能源车购置税减免延续）。
  • 两种结论，不硬凑：补证成立 · 置信度升高——找到直接依据的 8 条（如"燃油经济性标准→新能源汽车渗透强度"由双积分强制核算直接支撑、"投资项目节能减排评价→单位产品能耗限额强度"由"拟建项目应对照标杆水平建设实施"直接支撑）；已补证 · 维持原判——有依据但只支撑部分逻辑的 7 条，逐条写明为什么维持（如"电器 MEPS→终端电气化率"：效率下限降低的是电量消耗本身，不必然提高电力占比，GB 55015 支撑的是建筑能效维度）。
  • 数据对象 POLICY_VERIF：键 = "路径|描述符"，值含文件名、文号、施行日期、关键条款引文、官方原文链接。界面在政策侧栏每条映射下挂补证区块（徽标＋文件＋引文＋"查看政策原文"外链），置信度徽标随"升高"动态显示为"中→高"；统计条新增"联网补证 N 条（其中升高 M 条）"。
  • 键名合法性由测试把关：路径名与描述符名必须真实存在于平台数据——防止补证时手滑写错名字造成死数据。

边界

本批覆盖 15 条（8 升 7 维），中/低置信度合计 79 条，其余 64 条待续——多为间接影响类（税式支出、信息工具、自愿措施），其补证重点是"确认无直接定量落点、维持低置信度"而非升级。搜到的原文以国家级文件为主，京津冀三地专项文件（如协同机制相关）尚未系统核实，标"维持"的条目中含此类。补证只动置信度标注与依据展示，不改映射关系本身——映射是否成立仍由"模型要什么 input"倒推判断。

验证：test_verif.js 六项——15 条字段完整、st 与链接合法、键名双向合法、升高条目原置信度必为中/低、侧栏补证区块渲染（徽标/文号/链接）、统计条计数。

28　贝叶斯后验（真的参与计算）

纠正了什么

此前版本里「叠加贝叶斯」只是一个开关：打开后界面文案从「仅定性叙事」变成「贝叶斯（给区间）」，报告里也印出「叠加贝叶斯方法」，但代码中没有任何后验计算——这是对外承诺了没做的事，属于必须修的硬伤。现在这条开关会真的改变计算结果。

模型

  • 观测：每条判断（一个描述符影响另一个）背后有一个潜在影响值 μ；专家在 −3…+3 的七档量表上打分，等于把 μ 切档后的读数。多人模式下每位专家各给一个读数，按各自置信度定噪声（高 0.55 / 中 0.85 / 低 1.25）。
  • 先验：μ ~ N(0, 2.2²)，覆盖整个量表但很弱——没有假装有历史分布，这是弱信息先验，可在论文中如实写明并可替换。
  • 似然：七档切点取 −2.5/−1.5/−0.5/0.5/1.5/2.5，读数为 k 的概率 = 正态落在该档区间的质量。
  • 后验：在 [−3.25, 3.25] 上按 0.05 网格做数值积分，输出后验均值、标准差、5%/95% 分位、P(μ>0.5)、P(μ<−0.5)。

怎么用

  • 后验均值矩阵替换原打分参与 CIB 一致性检验（状态级精判优先于描述符级后验）；开关一开，自洽集就会变——这是它与「标签」的分界。
  • 区间最宽的若干条判断单独列出，作为人审优先级；「方向判不准」的判据是任一方向都未达到 80%，这样既能抓平后验（质量堆在 0 附近），也能抓双峰后验（两位专家 +3/−3 时两侧各 13%、中间 74%）。
  • 报告与配置摘要里的表述改为「贝叶斯后验（有序 logit，含 90% 区间）」，不再写「叠加贝叶斯方法」这类含糊说法。

边界

后验给的是判断的区间，不是模型参数的区间——参数区间来自状态定义（见第 29 节），两者不要混为一谈。单人模式下只有一条观测，后验主要由先验与置信度决定，区间偏宽是正常的；它衡量的是「这条判断有多不确定」，不是「这个值有多准」。状态级精判（逐格打分）目前仍按原值参与计算，尚未做逐格后验。

验证：test_bayes.js 七项——单条高置信 +3 的后验显著为正且下界大于 0；同分下高置信区间更窄；+3/−3 分歧呈双峰、无方向占优；同向两条比单条更集中；后验覆盖全部已打分条目；开关确实改变 impactVal 返回值；区间排序与判不准计数。

30　第 7 步分组导航（17 块按用途分四组）

怎么分

  • 可靠性（3）：逐层求解、稳健性检验、集成与分歧

  • 吸顶导航：导航条 position:sticky 贴在步骤条下方（top:118px），滚到哪一组都能切；小屏（≤820px）自动改为静态，避免占屏。
  • 状态常驻：导航右侧固定显示「已检验：自洽 N 组 · 检查 M 组（抽样）」——在「交付」组里也能知道检验跑没跑、结果多少，不必切回「结论」。
  • 全部展开：一键平铺 17 块，供通读或打印；再点回到单组视图。
  • 文案同步：情景筛选原写「下面的情景表与情景地图」，分组后它们不在同一屏，改为「切到『结构』组里的情景表与情景地图」。

边界

分组只影响看的方式，不影响计算、导出与报告内容；导出的配置文件与报告仍是全部模块的结果。分组不记忆用户上次选择——每次进入第 7 步都从「结论」开始，避免演示时停在意料之外的一组。

31　首页改版（删掉估算数字，改为真实统计）

原来的问题

首页那张「同一个情景，两种做法」是演示道具：三条情景的参数写死在 SCEN 常量里（描述符数、层数、矛盾组数、自洽组数都是手填），"需人工核对项"用 描述符 × 层数 × 3 − 8 估出来，"自动核对 0 项"是常数字面量，页面底部还写着"为估算量"。它和平台真实数据没有任何关系，一问就穿。

改法

  • 删掉估算链条：去除 SCEN、pickScen、三张 KPI 卡（100 / 12 / 4）与口径说明。
  • 统计改为实时计算（homeStatData()，每次渲染从数据算）：
    • 描述符 / 状态：遍历描述符树累加，同时累乘出组合空间（19 / 55 → 5.2 亿种）
    • 政策路径 / 映射：PALLC() 计条数与映射总数，并统计覆盖到多少个描述符（106 / 101，覆盖 17）
    • 中 / 低置信度映射：按映射条目的置信度分档累加（45 + 34 = 79）
    • 已核原文补证：POLICY_VERIF 条数，并数出其中 st==='升高' 的条数（15，其中 8）
  • 对比表只留定性：仍是七行（参数设定、语义翻译、跨层对齐、矛盾检查、参数来源、输出、自洽情景），但删掉全部数字与红绿强调色，只讲做法差异；表头明确写"只讲做法差异，不涉及任何量化结果"。
  • 版式改为概览入口，并重排标题层级：眉标（11.5px）回答"什么场景"——「京津冀 · 碳中和情景快速评估」；主标题（宋体 30px）回答"用什么方法、得到什么"——「用 CIB 把政策组合筛成自洽情景」；副标一行保留原口号「先把政策组合筛干净，再交给下游模型」；正文首句解释 CIB 全称（Cross-Impact Balance，交叉影响平衡）与本平台的边界（不算减排量）。其后是真实统计条、三步流程、对比表与进入按钮。

边界

统计条反映的是当前内置数据（数据集条目 + 映射表 + 补证表），换框架或换数据集后会跟着变，不是写死的宣传数字。"待补 79 条"是真实欠账，不是刻意隐藏；"覆盖 17/19"意味着仍有 2 个描述符没有政策路径映射。

验证：test_home.js 十九项——SCEN/pickScen 已删、四项统计条存在、路径/映射/中低置信/补证/升高五个数字与数据源逐一对齐、组合数按亿/万换算、对比表七行且无数字与黄绿底色、标题层级（眉标不含 CIB / 主标题含 CIB / 副标保留原句 / 正文解释全称）、页面不再出现"估算"字样。
