零、方法框架：一条政策到模型参数，要走三跳

后面按功能点逐项说明，但那些功能不是并列的几十个模块，而是同一条链上的不同环节。先把这条链说清楚，每一块才知道自己站在哪。

环节动作产物回答的问题例子
第一跳定性映射描述符这条政策动哪个变量？「工业差别电价」→ 单位产品能耗限额强度
第二跳定量换算状态区间这个变量取多少？「河北电炉炼钢 2030 ≥15%」→ 短流程占比这一档的落点
第三跳模型翻译模型参数怎么写进 GCAM / CHEER？→ share-weight、技术上限 / 下限、投资成本曲线

三跳各自靠什么，难在哪

第一跳：靠判断，判据是"模型里有没有这个变量"

这一跳没有算法，是人的判断，所以会错。判据只有一条：模型里有没有一个变量，装的就是这个描述符要设定的那个量。

  • 有，且就是它 → 政策直接落在这个变量上
  • 有，但装的是系数 / 曲线 / 潜力 → 属于间接影响，需要说明路径
  • 没有 → 说明这个量不是模型的内生变量，政策只能通过别的变量间接起作用

之所以要死守这条判据，是因为一旦放宽成"这条政策涉及哪个领域"，映射就会散——建筑能效标准会被连到"产业结构"，因为建筑属于产业；但它实际改的是建筑能效标准，不是产业结构。这在双边核对里已经出现过（见「三、下一步计划」）。

第二跳：靠算术，难在分母

政策文件给的是目标的自然口径，模型要的是它的口径，两者常常不是一回事：

政策给的区间要的缺什么
北京外调绿电 650 亿 kWh（2030）占全社会用电 %当年全社会用电量
森林覆盖率 45%（2030）碳移除 万吨/年林地面积、单位面积碳汇系数
可再生装机 8 GW（2025，天津）占一次能源 %利用小时数、总发电量
数据中心 PUE ≤1.15节能建筑占比不是同一个量，需要另找目标
炼化成品油占原油加工量 ≤40%三产占比不是同一个量，需要另找目标

要分清两种"不能直接用"：前三种是同一个物理量、单位不同，除一个分母或乘一个系数就能对上；后两种是压根不是同一个量，换算是换不出来的，只能另找直接目标。把这两类混为一谈，会得出"所有政策目标都能换算"的错误结论。

第三跳：靠文献与试跑

同一个政策目标，写进 GCAM 和写进 CHEER 的落点完全不同——GCAM 里多是市场份额权重与技术上下限，CHEER 里多是税率、转移支付与要素供给。这一跳在平台里体现为「目标模型」与「检验与导出」两步，具体参数取值需要文献依据与试跑校准，不属于本平台的自动化范围。

区间上的六个标记，说的就是这条链走到哪

区间依据由 RANGE_EVID 一张表管着，19 个描述符各归一类，界面上显示为徽标。前四个是证据强度，后两个是"被改过"的状态：

标记含义在链上的位置
政策目标政策数字的口径与区间一致，可直接用第二跳已完成
需换算有政策数字，但口径不同第二跳卡在分母
示例值政策文件里找不到对应目标第一跳有、第二跳无据
外生输入由 SSP 情景给定，政策不驱动不在这条链上
已改人工改过区间，原本的依据不再自动适用依据待重新标注
本辖区口径该辖区有独立区间，未沿用区域级第二跳按本地分母重算

四类证据强度的分布是：政策目标 3 个、需换算 5 个、示例值 9 个、外生输入 2 个，合计 19，正好覆盖全部描述符。数量在 app.js 里按 RANGE_EVID 的 k 字段统计得出。

这个分法的用处不是给区间贴标签，而是把"判断"和"算术"分开：第一跳是判断，可能错，要双边核对；第二跳是算术，只要分母有出处就可以复算复核；第三跳是工程，靠试跑验证。三类问题的排查方式完全不同，混在一起就只能笼统地说"还有待完善"。

通用性与落地：一套引擎，两层底料

这一节回答一个容易被误解的问题：这个工具到底是不是只能做京津冀？

平台的定位是两层，并不矛盾：

  • 方法要通用：目标不是只收集一套政策，而是面向任何地区——无论城市还是县乡，给一份政策文本，就能解译成对应的结构化描述符体系，流程不必重写。
  • 价值要落地：通用算法本身不构成优势，真正的差异在于它叠加了京津冀的本土化数据与政策口径——使用者不必自己再去找一套数。

所以定位是「通用引擎 + 本地底料」：

层内容是否可替换
引擎CIB 一致性检验、状态级精判、已知值锚定、跨层校验、逐层求解、路径分析、影响谱、相关性与地区无关，换任何区域都照跑
底料19 个描述符、55 个状态、106 条政策路径、三地政策目标与统计口径可整套替换——第 20 节的框架导入导出就是这条路径
案例京津冀绿色低碳发展路径SRT 的验证案例，不是方法边界

一句话：方法本身能搬到任何地区，但搬走之后要重新配底料；而京津冀这套底料（描述符体系 + 政策路径 + 三地目标值 + 分省区间）就是别人绕不开的部分。这也解释了为什么「通用性」与「落地」可以同时成立——通用的是算法，本地化的是数据。

工程上的直接推论是：平台上所有预设（描述符树、政策路径、区间、依据）都应当是可替换的配置，而不是写死在代码里。描述符树与政策路径已是数据表形式；v1.3 里还挂着「一键导入另一套分类框架的界面尚未做」这句话，v1.5 已经做完——描述符框架可导出为 JSON、改完再导入，另带一个"城市客运交通"示例框架用于演示同一套算法换一套变量。换框架的代价也写清楚了：只迁移变量结构，不迁移判断，打分要重做。

1　政策库与映射

解决什么问题

一条政策文本要先落成"动哪个变量"，才谈得上后面的打分。这一步不能靠临时想，得有一份可查、可追溯的清单。平台内置 106 条政策路径，其中 89 条来自 CCPID 国家库、17 条为京津冀地方补充；也可以上传自己的清单。

怎么实现

数据在 POLICY 数组里（app.js 中段），每条含路径名、类别、映射到的描述符与依据。渲染与交互集中在 renderPolicy()、pickPolicy()、polSidePanel()、polEvid()、applyPolicy()、uploadPolicy() 几个函数。政策原文依据另有两张表：

  • POLICY_EVID——58 条路径的工具级记录（法律文件、文号、定量口径、数据侧实证），键是路径名。
  • POLICY_VERIF——15 条逐条联网核实过的政策原文（文号 + 关键条款 + 官方链接），由 verifBlock() 渲染在政策侧栏，统计条实时计数。
// 政策侧栏的补证区块（节选）
function verifBlock(nm){ ... POLICY_VERIF[nm] ... }
function polEvidBlock(nm){ ... POLICY_EVID[nm] ... }

实际效果

点开任一条路径，右侧显示它对应的描述符、映射依据与政策原文。列表右侧的数字就是映射个数——映射为 0 不是缺陷，它表示这条工具不落在当前模型的变量口径内，这类记录本身就是结论：模型看不见某些政策。

「按政策库预填来源」把描述符的来源说明一次性写进状态定义，不必逐条手敲，这是 applyPolicy() 的作用。

验证

test_map.js 七项——映射个数与列表一致、零映射条目仍渲染、侧栏依据字段完整、上传清单解析、预填不改动已手写的来源、统计条计数、政策库条目键名唯一。

2　交叉影响打分（含 AI 预填与人工审核）

解决什么问题

CIB 的全部输入就是一张 n×n 的影响矩阵：行描述符取某个状态，会促进还是抑制列描述符的某个状态。问题的难点不在算法，而在谁来判断、判断怎么留痕。

怎么实现

19 个描述符两两组合，方向有意义（甲影响乙与乙影响甲是两条），所以按有序对计：19×18 = 342 对。矩阵渲染在 renderCim()，逐格写入走 setV() / setConf() / setWhy()；AI 预填是 aiFill()，人工审核留痕是 toggleRev()，清空走 clearCim() / resetCim()。

0 的语义是这一版最重要的一处口径修正。原先点一个空格子，平台自动填成「0 / 低置信度」，AI 预填也把 342 对里没找到直接影响的全部写成 0 加低置信——这等于把「判为无关系」和「还没判」合成了一件事。现在：

  • 0 表示「两者之间没有直接关系」，是一个判断，不是「没把握」。引的是导师 2026-10-21 录音当场纠正的原话：「不是置信度低，他俩之间没关系」。
  • 影响分与置信度是两条独立的轴，分开填。可以判成 0 却高置信，也可以填 +2 却低置信。
  • 真正没做判断的格子留空，界面显示「·」，与填 0 不是一回事。统计里「已判 / 未判 / 判为 0 / 低置信度」四项分开计数。
  • AI 预填只写自己确实找出直接影响的那几条，其余留空；预填过的格子带 AI· 标记，人工改过分数或置信度后标记自动消失。

格子里的置信度与 AI 标记直接写在格内（不是只靠边框颜色）——这是导师点名的改动，原先颜色是唯一线索，一屏看下来分不清哪些格还没人管。

矩阵的平衡预览在 cimBalance()，状态级展开表在 stTable()，逐格写入走 setSt()（见第 8 节）。

实际效果

342 对判断在一个可滚动矩阵里完成，每格显示分数、置信度与依据；复核时按置信度排序，优先看低置信度的格子——那些通常缺少原文依据或专家意见不一致，是结论最脆弱的地方。

验证

test_cim.js（矩阵渲染、逐格写入、清空、依据字段）、test_zerosem.js（0 与留空的区分、四项计数、0 与「低置信」是两条独立的轴）、test_rng.js（区间与矩阵联动）各若干项。

3　自洽情景计算（CIB 一致性检验）

解决什么问题

把 19 个描述符的 55 个状态组合起来是一个天文数字，平台要回答的是：哪些组合内部不打架。判的不是"好不好"，而是"彼此是否互相抵消"。

怎么实现

核心在 enumCore()（枚举与判定内核）与 runCIM()（入口），自洽情景卡片渲染在 checkResult() / scenCard() / scenDetail()。算法分三步：

  1. 枚举候选组合。全空间是各描述符档位数之积，19 个描述符合计 516,560,652 种（homeStatData() 实时算出，不是写死的宣传数字）。
  2. 算影响平衡值：某个状态受到的其余状态影响之和，即 evalCombo()。名字在这一版统一——同一个量原先有两个名字且指向相反（一处叫「主动和」，术语表又定义「主动和 = 施加」），判定实际取的是「该状态从其余状态承受到的总量」。现全部改名为影响平衡值。
  3. 筛选：影响平衡值最大、且不与其他判断矛盾的组合，判为自洽。

组合数超过预算时自动改为固定种子抽样（mulberry 随机数、comboSample()），此时自洽情景数是下限，界面已注明。矩阵指纹由 cimSig() 生成——打分动过之后结果自动提示过期。

「主动和 / 被动和」只保留给主被动图的两根轴，界面与术语表双向注明它与「影响平衡值」不是同一个数，避免再出现同名不同义。

实际效果

检验结果卡列出全部自洽情景，每组可展开看逐描述符取值与依据；另有「你选的情景」单独判定——选中组合是否自洽、若不自洽差在哪一条判断，走 selectedCombo() / checkSelected() / rangeStat()。

验证

test_sel.js 八项、test_layered.js、test_stlvl.js 六项（精判优先于描述符级展开）等。

4　影响关系图

解决什么问题

矩阵是一张表，看不出结构。哪几个描述符处在影响网络的中心、哪些几乎孤立，图形比表格快。

怎么实现

renderImpact() 把当前打分画成有向图：每个描述符是一个节点，连线代表影响；赭色是促进、靛色是抑制，线越粗表示影响越强。悬停任一连线可看到这条判断的依据（依据文本来自矩阵的 why 字段）。

实际效果

图上能直接看出"枢纽型"描述符与"被指向型"描述符的差别。主被动图在本版已删除卡片——它与影响关系图重复，引擎里的计算保留。

验证

test_ens.js 与 test_tip.js 覆盖图中节点数、连线条数与依据文本存在性。

5　情景表

解决什么问题

几十个自洽情景，逐个展开看太慢。需要一眼扫出"哪些情景在哪些描述符上其实是同一档"。

怎么实现

renderTableau() / renderAP() 渲染情景表：列是自洽情景，行是描述符；相邻情景里取同一个状态的格子自动合并并着色，几十个情景的异同一眼扫出来。合并的是相邻列，不重排情景顺序——重排会让读者跟不上。

实际效果

同色格子成块出现的地方，说明这一组情景在这些描述符上没有分歧；某个描述符每格颜色都不同，说明它是真正的分歧点。

验证

test_anc.js 与 test_filt.js 覆盖列数、合并逻辑与筛选后跟随。

6　情景报告

解决什么问题

一次配置要能拿给别人看：选了哪些描述符、每个分数怎么判的、哪些情景自洽、矛盾在哪、参数的依据是什么。

怎么实现

reportData() 汇总数据，buildReportHTML() 生成报告主体，openReport() 开模态框。三条出口：downloadReport()（HTML）、downloadReportJSON()（JSON，交给别的系统）、downloadReportDoc()（Word）。

Word 出口走的是「HTML 套 Word 版式」路径：screenCSS() 提供屏幕样式，downloadReportDoc() 另拼一份 A4、宋体正文、黑体标题、实线表格的 Word 版式，以 .doc 下载，双击即改，不装库、不依赖服务端。

实际效果

报告包含配置摘要、判断链、自洽情景集、矛盾清单与双锚点时间轴。不能携带网页里的交互展开内容——Word 版式是静态的，折叠段在报告里展开为完整段落。

验证

test_reportdoc.js、test_export.js 覆盖三种出口的字段完整性与版式关键样式。

7　状态半定量化（取值区间）

解决什么问题

「高速 / 中速」这类标签本身是模糊的：5.1% 算高速还是中速？给每个状态挂一个数值区间，定性标签就变成半定量档位。

怎么实现

区间预设表 RANGE_PRESET 在 app.js 第 479 行起，覆盖 19 个描述符的 55 个状态。渲染与编辑在 renderStates() / stTable() 一带（状态面板的每行由 renderStates() 铺出，行内展开表走 stTable()，逐格写入走 setSt()），编辑走 editRange() / saveRange()；重命名与增删走 renState() / delState() / doAddState()（addState() 是入口壳）。

区间伸缩的合法性由 rngIssues() 检查：相邻档位重叠、空档都会提示；rangeSize() 算当前勾选范围下的组合数。

区间贯穿打分侧栏、情景表、情景详情与情景报告四处——改一处，四处同步。

实际效果

标准不必只有一套：使用者可以换自己的口径，改完的区间会标成「已改」（EVID_WORD.user），原依据不再自动适用。同一描述符在不同辖区可以有不同边界（见第 11 节）。

区间不是装饰——它通过「已知值」与「取档」两处真正参与计算，见第 9、22 节。

验证

test_rng.js、test_anc.js 覆盖区间读写、非法区间提示、重命名后引用同步。

8　状态级精判（把打分真正打到状态对）

解决什么问题

描述符级打分是一个妥协：19×19 的格子，每格代表"整体倾向"。但「产业结构加速服务化」影响「一次能源结构」的哪一档，与影响「推进迟缓」那一档，方向可能相反。全填满要 55×55 格，没人填得完。

怎么实现

每条判断可展开到状态对逐格判断，展开表由 stTable() 渲染，逐格写入走 setSt() / clearSt()。取值规则：精判值优先进入一致性检验，未精判的才按整体倾向自动展开。

impactVal()（app.js 第 827 行）是唯一的取值入口，它按"状态级 → 描述符级 → 后验均值"的顺序取值，所以打开贝叶斯后验时也走这里，状态级精判仍然优先。

实际效果

不强迫用户填满全部格子，又真正支持状态级判断。填充后自洽情景数会变——因为进入检算的数值变了，这是它"真的生效"的证据。

验证

test_stlvl.js 六项——展开表维度、写入与读取一致、精判值覆盖描述符级、清空回落到自动展开、自洽数随之变化、后验开启时优先级不变。

9　已知值（数值锚定下沉到状态面板）

解决什么问题

区间把标签变成数值之后，下一步问题是：这个描述符今年到底取多少，是已知的。比如经济增速已知在 4.5–5.0 之间——那么凡是区间与它完全不相交的状态，这套假设在数值上就站不住，不必再拿去比对。

怎么实现

v1.3 里这是一个独立卡片。v1.5 下沉到每个描述符的状态面板里，与状态勾选同一层输入——"选完状态顺手定已知值"，不必再回到别的页面。输入行由 ancRowHTML() 渲染，解析与写入走 parseAnc() / setAnc() / clearAnc() / ancOf()，取值过滤走 ancAllowed()，冲突检测走 ancConflicts()，总览走 ancSummaryHTML()。

三条规则：

  • 只有与已知值完全不相交的状态才被排除；部分重叠的保留，因为它仍可能与已知值相容。
  • 没有区间不排除。该描述符的区间要是空着，锚定对这一项不产生作用。
  • 锚定的作用在检算前：搜索空间因此收窄，检验结果随之改变。与情景筛选的区别就在这里——筛选在检算后过滤展示，不改变结果。

枚举不是"全空间生成再过滤"，而是按允许集算基数后混合基数枚举（enumCore() 里的 allowed→radix→space 三段），否则 5 亿的空间根本进不去。无解时直接拒算并提示，而不是算出空集让人以为程序坏了。

如果某个描述符的已知值把它的所有状态都排除了，页面会明确报错：「锚定把这个描述符的所有状态都排除了——检验会直接报错，请放宽已知值或改区间。」另一种要显式提示的情况是选中的状态与已知值不相交：它在枚举里确实不会出现，但界面上仍显示为已选中，ancConflictHTML() 专门提示这一点，否则用户以为它被检验过了。

实际效果

总览条只讲"收窄了多少"：给 3 个描述符设定已知值，组合空间可以从 27 种降到 9 种这类量级的收窄直接写在页面上（ancSummaryHTML() 里 before → after 的实际乘法）。前提是区间本身可信——如果区间是示例值，锚定的结论也只到示例精度。

验证

test_anc.js——完全不相交才排除、部分重叠保留、无区间不排除、全部排除时报错文案、选中状态冲突提示、收窄前后计数、清除后恢复。

10　跨层一致性与约束前置

解决什么问题

横向 CIB 只管同一层内的描述符互不打架。但层级之间还有一层约束：上级定「目标节奏（20–30%）」，下级不能选「推进迟缓（10–20%）」。这是纵向的一致性问题。

怎么实现

层级树为四层（LAYERS）：

层级角色说明
国家级给定层取值来自国家政策目标，是外部条件，不参与组合枚举（LAYERS 里 g:1）
区域级合计口径三地合计 10897 万人、三地加权增速约 5.3%
省级分省口径北京 2180 万 / 天津 1363 万 / 河北 7354 万；增速 5.4% / 4.8% / 5.6%
市级分市口径河北 11 个地级市，合计 7354 万

判定规则是档位不反向：相邻层级之间比档位差，0 一致、1 允许的梯度、差 ≥2 判冲突，另有"取值区间不相交"也判不兼容。规则实现在 xlayers() / xlPickOf() / xlReason() / xlSet() / xlPickHTML() 一组函数里。

这一版最大的改动是判定的时机：原先要等逐层求解跑完、再回头比相邻层，用户选的时候不知道会不会冲突，算完才发现。现在约束前置——第 3 步按层给每个描述符选档位，选定的上层档位立刻筛下层：与它方向相差 ≥2 档、或取值区间不相交的档位直接置灰不可选，原因写在选项的悬停文字里（xlReason() 生成）。这样枚举出来的组合天生满足跨层要求。

平台不替用户改档。上层改动后，下层原来选的档位若已不相容，只清空并说明原因，由用户重选。理由写在界面文案里：档位冲突可能是真实的政策张力，替用户消解它等于替用户做政策判断。v1.3 里那个"冲突可一键调到相邻档"的动作随之取消，第 7 步的跨层一致性台账整块删除——删的是事后台账，判定本身移到了选档位的时候。

实际效果

选档位时就看得见后果，不会出现"算完几十秒才发现两个层级打架"。只勾一层时，跨层核对不启用，平台等同于在单层内做一致性检验。

验证

test_scope.js、test_layered.js 覆盖四层结构、档位差不反向、区间不相交过滤、置灰选项带原因、上层改动后下层清空且给出说明。

11　区间分层（同一描述符，不同辖区不同边界）

解决什么问题

「加速服务化」这个名字在北京与河北都成立，但边界完全不同：北京 2025 年三产占比 86%，河北 55%。用一套区间会同时错位——86% 落在"加速服务化"里，55% 也落在里面，档位就失去了区分度。

怎么实现

整套区间按辖区分层：区域级（京津冀）、北京、天津、河北四套，界面顶部切换（renderScopeBar()），取值走 rangeOf(nm, scope)，辖区的建立与读取走 baseOf() / setScope() / dropScopeOverride()，缓存清理在 clearScopeCache()。辖区名由 SCOPE_NAME 提供。

关键设计：状态结构（有哪几档）全辖区共享，只有数值分开。因为"加速服务化"这个档位在三地都成立，需要分开的只是它的数值边界。描述符定义里的 defsOf() 负责合并"共享结构 + 本辖区数值"。

已按政策与统计数据预填两个描述符的省级口径（SCOPE_NAME 约定）：产业结构按三地 2025 年现状 86% / 65% / 55%；一次能源结构按北京 2030 年 25%、天津 2030 年 16%。其余 17 个因缺少分省数据仍沿用区域级，卡片上标明「本辖区口径」的徽标区分（EVID_WORD.scope）。改省级区间不会污染区域级，可一键恢复（dropScopeOverride()）。

实际效果

要做三地之间的真正差异比较，就得先把省级区间按各省统计口径补齐——目前只有 2 个描述符有分省数据。这一条写在边界表里。

验证

test_scope.js——四套区间独立读写、切辖区不互相污染、徽标随来源变化、一键恢复、导出跟随当前辖区。

12　逐层求解（跨层约束真正进入枚举）

解决什么问题

约束前置解决的是"选的时候别选错"，但真正要回答的是：上级取某个值时，下级还剩哪些可能。这需要把上级的取值当作下级的约束，进到枚举里去算。

怎么实现

这一段在第 7 步的默认收起折叠段里（勾了多个层级才出现），由 runLayered() / solveLayer() / renderLay() 实现。核心思路：组合是否自洽只取决于组合自身，与上级约束无关——所以整层只判一次，再按各组的允许集归桶筛选。上级的取值转成下级的约束，下级与它区间不相交的状态直接不进枚举，而不是算完再比对档位差。

预算常量：LAYER_BUDGET = 250000、LAYER_KEEP = 80000（app.js 第 1101 行）。小空间精确求解，大空间改固定种子抽样，此时自洽数为下限。每层展示上限 600 组，超出标「+」。

输出为带完整层级路径的组合（区域情景 → 省情景 → 市情景），路径末节挂上级的 scope 与组合。这一条曾经有个隐蔽缺陷：旧代码读顶层的 scope/cb，而它实际挂在路径末节，导致链式层级的上级约束从未传入——全零矩阵的旧测试恰好掩盖了它，v1.3 重写内核时修复。

实际效果

19 个描述符三层实测：强耦合 0.85 秒/层，稀疏场景 2.6 秒跑完全程。上级某情景若让下级完全无解，会单独计数——那不是程序出错，那就是结论。

验证

test_layered.js——单层结果与横向检验一致、上级约束真的收窄下级、无解单独计数、路径完整可追溯、预算切换后自洽数为下限并标注。

13　多专家集成（分人打分、分歧裁定）

解决什么问题

342 对判断由一个专家打分，主观性无处暴露。让 2–3 人各打一份，分歧就成了可见的东西。

14　情景地图与情景筛选

解决什么问题

自洽情景往往几十上百个，逐个看不过来。两件事要分开：整体格局（哪些情景聚在一起、哪些描述符被锁死）与定向反查（我想看"如果三产占比很高"那一部分的可能）。

怎么实现

情景地图对应德国软件的 Scenario maps，含两视图，切换走 setMapMode() / renderMap()：

  • 情景簇聚类图（renderCluster()、相似度 scenSim()、聚类 scenClusters()、族定义 familyDesc()）：把自洽情景按取值相似度聚成簇，族内所有情景取值都一致的描述符才写进该族定义，族与族的差别即这套假设体系下真正的分歧点。聚类允许差异固定为描述符数的 30%，不可由用户调整；自洽情景超过 60 个时只对前 60 个做布局，图上注明。
  • 状态分布热力图（renderHeat()、配色 heatColor()）：给出每个描述符在各档位上的占比，几乎只有一个取值的会被标为「被其他条件锁死」。

情景筛选对应德国软件的 Selection Manager，走 filtList() / setFilt() / clearFilt() / renderFilt()：对任意描述符指定要求取值，多条件取交集（filtList() 里逐条 AND），无条件时返回全量。每个条件旁实时显示命中数与占比；条件互斥导致 0 命中时明确提示「这些状态不可能同时成立」——零命中本身就是一条结论。

本版把筛选从独立卡片并入检验结果块（index.html 里 #filtBox 紧跟在 #layFold 与一段折叠说明之后），因为它与检验结果读的是同一批数据。筛选只作用于展示层（情景表、聚类图、热力图跟随），检验结果不变——这一条与「已知值」正好相反，两者在界面上并列写明。

实际效果

"我想知道在这种假设下还剩哪些未来"——指定条件后，情景表与地图立刻只看命中的子集。目前只有"指定某描述符取某一档、多条件取交集"这一种条件形式，德国软件另有若干形式化筛选程序，暂未实现；筛选结果暂不随导出生效。

验证

test_filt.js——单条件命中数、多条件交集、零命中提示、清空回全量、筛选不改变检验结果、地图跟随筛选。

15　影响路径分析（间接传导链）

解决什么问题

矩阵里两个描述符之间没有打分，很容易被理解成「互不影响」。但影响是可以绕一层的：煤炭消费结构不改，电力部门就难以清洁化；电力不清洁，终端电气化反而增排。三者两两之间也许只有一段直接判断，合起来却是一条完整的传导链。

这一块补的是「为什么两个看起来无关的描述符会互相影响」。它也直接对应多尺度：国家目标 → 省域结构 → 市级排放，本质就是一条路径。

怎么实现

  • 搜索：findPaths() 在已选描述符上做深度优先遍历，只走非零影响的边，不重复经过同一节点，收集全部 2—3 段（最多 2 个中间环节）的有向链。统计与排序在 pathStat() / pathRanked()，渲染在 renderPath()。
  • 强度：一条链有多强，取决于它最弱的那一段——+3 接 +1，整体只按 +1 算。不用连乘也不用求和：连乘会因符号与量级迅速失真，求和会把一条「中间被卡死」的链算得比实际强。
  • 方向：看负号个数，偶数个为净促进、奇数个为净抑制。
  • 排序：先按最弱环节的绝对值降序，同强度时短链优先。
  • 隐性关联：hiddenLinks() 扫全部配对，列出直接判断为 0、却存在间接通路的那些——它们提示矩阵里可能漏了一条关系。点击某一行即可把起点终点切过去细看（setPath()）。
  • 提示：若直接判断已填 0 但存在间接链，界面明确写出「这两个描述符其实有关系，只是绕了一层」，建议回到矩阵补直接判断，或在依据里注明「经某某间接影响」。

一个实现上的坑（值得记）

第一版把段数判据写成 if(path.length >= maxSeg) return;，结果三段链永远找不到——走到第二个中间节点时段数已到上限，程序在「判断是否到达终点」之前就返回了。正确判据按段数（节点数减一）而不是节点数：seg = path.length - 1; if(seg > maxSeg) return;。测试里专门留了一条「A→B→C→D 应找到 1 条 3 段链」，就是用来卡这个的。

另一条判据：到达终点后立即返回，不再延伸——否则 A→B→C→B 这类绕回起点的链会被重复计入。

实际效果

选定「一次能源结构 → 终端电气化率」这类起终点，界面会列出所有 2—3 段通路，每条都标出净促进 / 净抑制与瓶颈强度。如果这两格之间本来填的是 0，而下面又挂着两条链，就等于被指出来：矩阵漏了一条关系。

该模块与「影响关系图」互补：关系图看直接边的全局格局（谁最中心），路径分析看两点之间的传导（为什么会传过去）。链上每段的依据目前仍需回到打分矩阵查看，尚未在路径行内联——这一条写在边界表里。

验证

test_path.js 八项——基本传导（+2 接 +3 → 强度 2）、方向奇偶（+2 接 −3 → 净抑制）、三段链、段数上限、无通路返回 0、隐性关联识别、提示渲染、描述符不足 3 个时给提示而非报错。

16　影响谱（外部冲击会挤掉哪些可能）

解决什么问题

情景集本身是一张「哪些组合站得住」的地图。决策者更常问的却是另一种问题：如果某件事被强行实现——比如 GDP 增速被压到低位、或某条硬指标必须达成——地图上还剩下什么？

德国软件把这类分析叫 Influence profile：逐个把某个状态「钉死」，重算情景集，再与基准对比。本版实现的是其中的定性版——只回答「有没有」和「变了没有」，不统计频率变化。

怎么实现

  • 复用同一套枚举：一致性检验的内核是 enumCore()。把某个描述符的可选集合收成只有一个状态（buildIMP() 与 runProfile() 负责组装），相当于外部力量把它钉死了。
  • 基准与对照：先算不强制时的自洽集，记下每个状态是否在某个自洽情景里出现过（presence，而不是只看情景条数）；再对每个状态逐个强制、重算，比对两次的 presence。入口是 computeProfile()，选点 profPick()，渲染 renderProf()。
  • 两种结果：被挤掉（基准里有、强制后没有）；整行为 0（该状态下没有任何自洽情景）。后者是最强的结论——这条冲击与当前全部判断不相容。
  • 预算控制：状态多时逐次强制会变成几十上百次重算。按状态总数给每次强制分配抽样量，总量控制在约 40 万个组合；有抽样时在界面注明，并说明「方向可靠、具体条数会浮动」。
  • 明细：点任一行，展开该冲击后被挤掉的具体状态清单（哪个描述符的哪一档）。

一处必须讲清的方法边界

本版把「强制」实现为硬约束。这在数学上意味着一个性质：强制后的自洽集必然是基准集的子集——因为判定规则没变，只是可选的组合变少了。所以本版只会出现「被挤掉」，不会出现「被打开」。

而德国软件的手册里明确有 [+] 标记（原本不存在、强制后出现）。它之所以能做到，是因为它把外部冲击当作会改写矩阵的影响来处理（相当于新增一条外部影响，改变了各状态的影响平衡），而不只是限制组合空间。那是另一种建模，需要额外定义「这条冲击如何影响其他变量」——本版没有采用，界面上也如实标注了这一点。

这是有意为之：宁可少一个标记，也不要做出一个看起来有、实际靠不住的结论。 如果将来要补这种模式，正确做法是让用户为冲击填写影响向量（对哪些描述符、多强），而不是从「强制一个状态」里推出连带的矩阵变化。

实际效果

它回答的是「哪些门会被关掉」：某个状态被钉死后，哪些原本可能的搭配不再成立；哪些状态被钉死后整个情景集清空。对政策讨论来说，后一类往往比前一类更有信息量——它直接说明「这件事和目前这套判断体系不相容」，要么放弃它，要么修正判断。

与相邻模块的分工：情景筛选是「按我的要求过滤已有情景」（展示层）；已知值是「按已知数值排除状态」（检算前）；影响谱是「假设某个状态被外部力量钉死，整套情景集会怎么变」（检算后重算）。三者的作用点分别为展示、检算前、检算后。

验证

test_prof.js 五项——全零矩阵基准 27 组、强制任一状态后 9 组、无状态被挤掉；让某个状态永远不是最优时强制它得到空集（同类状态同样为空，共 2 行）；设计一条只在特定取值下成立的边，强制该状态后另外两个状态被挤出（21 组 → 3 组）；渲染含表格、基准行、空集提示与硬约束说明；描述符不足时返回错误而非崩溃。

17　相关性分析（哪些状态总是绑在一起）

解决什么问题

情景表能看出「有哪几十种搭配」，但看不出「哪些搭配其实是同一件事的两种说法」。相关性分析回答的是后者：某些状态是不是总一起出现？——如果「经济高速」和「产业结构加速服务化」在几乎所有自洽情景里都同进同出，那它们在讨论中其实是一个判断，不该当成两个独立的自由度。

怎么实现

  • 系数选择：状态只有「出现 / 不出现」两种取值，因此用 Pearson φ 系数（等价于两个二值变量的皮尔逊相关）。手册 6.13 用的也是这个公式，结果以整数百分比呈现。计算在 computeCorr()，选点 corrSel()，渲染 renderCorr()。
  • 统计口径：以全部自洽情景为样本，而不是情景表里展示的前若干条——展示是截断的，用来算统计量会失真。为此给枚举内核加了 keepAll 参数（上限 8000 条，超出时界面注明）。
  • 只算跨描述符配对：这是必要的取舍。同一描述符的不同状态天然互斥，φ 恒为 −100%，若一并计入，「强关联」列表会被这些构造性结果占满，真正有价值的信息被淹掉。
  • 无区分度的状态不计：从不出现、或每组情景里都出现的状态，其方差为零，φ 无从计算——按手册做法留空。
  • 小样本警示：情景数 < 20 时界面直接提示「系数可能不稳定」。手册原话是 correlation coefficients of small scenario sets may lead to artificial results。
  • 两种视图：强关联列表（|φ| ≥ 80%，带条形和正负配色）看全局捆绑关系；单个状态的关联谱看某个状态跟谁最亲近（对应手册的 correlation profile）。
/* φ 系数（等价于二值变量的皮尔逊相关） */
nAB = #(A 与 B 同现)      n10 = nA − nAB      n01 = nB − nAB
n00 = S − nA − nB + nAB
phi = (nAB·n00 − n10·n01) / sqrt(nA·(S−nA)·nB·(S−nB))

两处必须说清的边界

① φ 不是因果。它只说「是否同进同出」。两个状态高度相关，可能是因为一个推动另一个，也可能因为同受第三个变量驱动（例如都受「碳价」影响）——先后与因果要看交叉影响矩阵和影响路径。界面底部写明了这一点。

② 相关会随判断变。换一套打分、或加一个已知值，情景集就变了，系数也随之变。它描述的是「在当前这套判断下这些状态怎么搭」，不是京津冀的客观属性。汇报时应说明是在哪个情景集上算的。相关也不能跨情景集比较。

实际效果

典型读法：若「高速增长」与「加速服务化」的 φ 达到 +90%，说明在这套判断下二者几乎不可分——讨论时不该把它们当成两个可以独立选择的旋钮；若某个描述符的若干状态与谁都只有弱相关，说明它在这套体系里相对独立，是个可以单独发力的抓手。

验证

test_corr.js 七项，其中两处用手算对照：设计一条只在 A 取第 1 档时成立的边（21 组情景），手算 φ(A1,B1)=+47%、φ(A1,B2)=−26%，程序输出一致；构造完全耦合的三档映射（9 组情景），φ(A1,B1)=+100%、φ(A2,B3)=+100%、φ(A1,B3)=−50%，与手算一致。另验同描述符配对不出现、全零矩阵下所有 φ 均为 0、小样本警示与关联谱渲染、描述符不足时返回错误。

18　政策依据接入（文件名、口径、数据侧实证）与映射补证

解决什么问题

政策库里每条路径都指着一两个描述符，但此前只有结论、没有出处：为什么「节能技术改造补贴」对应「工业节能改造强度」，界面上只有一句模型侧写的理由，看不到政策本身的证据。

而数据集的「工具总览」表里其实有：法律文件名称、具体口径（含定量目标的原文摘要）、对应描述符。这些此前只存在于 Excel 里，平台上看不到。

怎么实现

  • 聚合而非手抄：脚本读数据集 409 条工具，按「路径」聚合，得到 58 条路径的证据记录（工具数、法律文件最多 2 份各截 44 字、定量口径最多 1 条截 120 字、数据侧实证描述符最多 3 个、涉及地区最多 3 个），生成 POLICY_EVID 数据对象，不手敲，避免与数据集脱节。
  • 界面呈现：政策库点任一路径，侧栏顶部出现「政策依据（数据集 · 工具总览）」区块——工具级记录数、涉及地区、书名号文件名、口径引文，由 polEvidBlock() 渲染。
  • 两侧比对：把数据侧已填的描述符与模型侧映射逐条对照，给出三类结果——一致、模型侧另有（数据侧尚未建立）、数据侧另有（可能是绕一层的映射，也可能是口径差异）。
  • 没有记录的照实说：58 / 106 条路径有工具级记录，其余 48 条在数据集中尚无条目，区块直接写明「映射只能靠模型侧推断，置信度按中/低处理」。

映射补证：拿政策原文来对质

政策库里标「中 / 低」置信度的映射此前只有一句模型侧推断理由，没有政策实体支撑——这是边界表里挂着的欠账。补证不是把理由重写一遍，而是找到文件、文号、关键条款，再决定这条判断是站得住还是该降级。

  • 按描述符聚类核实，不逐条硬搜：把「中」置信度映射按目标描述符聚成约 10 组（新能源汽车、建筑能效、能耗限额、碳价、本地可再生、区域互济、产业结构……），每组找 1—2 份权威政策原文，组内条目共享依据。本次核实到的文件包括：发改价格〔2023〕1501 号（煤电容量电价）、五部门令第 64 号（双积分修订）、财税〔2018〕74 号（车船税）、GB 55015-2021（建筑节能通用规范，全文强制）、发改产业〔2023〕723 号（工业能效标杆 / 基准水平）、生态环境部碳市场扩围方案、发改委令第 7 号（产业结构调整指导目录）、发改能源〔2019〕807 号（可再生电力消纳保障机制）、国务院令第 779 号（生态保护补偿条例）、财政部等 2023 年第 10 号公告（新能源车购置税减免延续）。
  • 两种结论，不硬凑：补证成立 · 置信度升高——找到直接依据的 8 条（如「燃油经济性标准 → 新能源汽车渗透强度」由双积分强制核算直接支撑、「投资项目节能减排评价 → 单位产品能耗限额强度」由「拟建项目应对照标杆水平建设实施」直接支撑）；已补证 · 维持原判——有依据但只支撑部分逻辑的 7 条，逐条写明为什么维持（如「电器 MEPS → 终端电气化率」：效率下限降低的是电量消耗本身，不必然提高电力占比，GB 55015 支撑的是建筑能效维度）。
  • 数据对象 POLICY_VERIF（15 条）：键 = 「路径|描述符」，值含文件名、文号、施行日期、关键条款引文、官方原文链接。界面在政策侧栏每条映射下挂补证区块（徽标＋文件＋引文＋「查看政策原文」外链），置信度徽标随「升高」动态显示为「中→高」；统计条新增「联网补证 N 条（其中升高 M 条）」。
  • 键名合法性由测试把关：路径名与描述符名必须真实存在于平台数据——防止补证时手滑写错名字造成死数据。

一处必须讲清的边界

区块底部写着一句话：文件名与口径能证明「这条政策存在」，不能单独证明映射关系成立。

这两件事必须分开。数据集告诉你「北京有一份《碳排放权交易管理办法》，口径是对重点排放单位实行配额管理」；但「它对应到本模型的哪个变量」仍是模型侧依据「模型要什么 input」倒推出来的判断。把前者当成后者的证据，是这类工作最常见的自欺。 所以本版的做法是：证据列在一边，判断列在另一边，两者并置供人核对，而不是把文件名当成映射的授权书。补证只动置信度标注与依据展示，不改映射关系本身。

本批覆盖 15 条（8 升 7 维），中 / 低置信度合计 79 条，其余 64 条待续——多为间接影响类（税式支出、信息工具、自愿措施），其补证重点是「确认无直接定量落点、维持低置信度」而非升级。搜到的原文以国家级文件为主，京津冀三地专项文件（如协同机制相关）尚未系统核实。

实际效果

以「排放交易体系（ETS）」为例，侧栏会显示：工具级记录 2 项、涉及北京 / 天津、《北京市碳排放权交易管理办法》《天津市碳排放权交易管理暂行办法》，以及一段口径引文；下面才是我方映射。用户能一眼看出这条判断有没有政策实体支撑。

验证

test_pevid.js 七项与 test_verif.js 六项——58 条证据、57 条能对上政策库名称、字段形状无异常、依据区块渲染（工具数 / 文件名 / 口径 / 边界说明）、无记录路径显示「尚无工具级记录」、统计条与列表「证」标记数量；15 条补证字段完整、st 与链接合法、键名双向合法、升高条目原置信度必为中 / 低、侧栏补证区块渲染、统计条计数。

19　稳健性检验（判断改一档，结论还站得住吗）

解决什么问题

一致性检验的输入是人给的 −3 到 +3。审稿人一定会问：这些打分如果在合理范围内晃一下，自洽情景还站得住吗？哪些结论是骨架、哪些是碰巧？这一问题的现实背景是：「AI 打分、人来审核」若要落地，前提就是知道该把人审的力气花在哪，而不是笼统地"再检查一遍"。

怎么实现

  • 扰动重算（蒙特卡洛）：把每条已填判断按置信度随机改 1 档——低置信度改动的概率 0.5、中 0.25、高 0.08（CONF_P，app.js 第 4050 行）——整轮重算，默认 30 轮（可选 10 / 30 / 60）。统计每个状态在扰动后的出现率，≥90% 判「稳健」、50%—90% 判「敏感」、<50% 判「脆弱」。入口 runRobust()、轮次 setRobR()、计算 computeRobust()、渲染 renderRobust()。
  • 固定组合集：基准与每一轮扰动都评估同一批组合（全枚举或固定种子抽样 2000 个）。只有组合不变，才能回答「同一条情景在判断改动后还自不自洽」，而不是比较两个毫不相干的集合。
  • 单格翻转：逐条把某格改 ±1，统计基准自洽集（前 80 个）里有多少条被推翻。翻掉比例最高的 10 条列成表——这就是「最该先找人复核的判断」。人审的力气应该按这张表分配，而不是平均撒。
  • 过期提示：检验结果带一份矩阵指纹（cimSig()），打分再动过就提示「数字已对不上当前判断，建议重跑」。
  • 计算内核：单独实现 buildIMP()（按给定矩阵展开状态级影响值）与 evalCombo()（判单条组合自洽），判据与主检算 enumCore() 完全同一条；测试里用全枚举比对过两条路径逐格一致。

边界（必须讲清）

结果不是概率。出现率 90% 不读成「这个情景有 90% 的可能发生」——它只衡量「判断晃动会不会改变结论」。CIB 方法本身不给概率，这里也不给。扰动幅度固定为 ±1 档：更大幅度的改动属于「换一套判断」而不是「同一判断的误差」。空间过大时为抽样近似（界面已标注）。把幅度做成可调档位、并支持从"最该复核的判断"直接跳到对应打分格，是下一步计划里的可选项。

验证

test_robust.js 六项——evalCombo 全枚举与 enumCore 计数一致（27 组合逐格比对）、无打分报错、扰动轮次与状态行数、出现率落在 [0,1]、同种子确定性（两次结果序列完全相同）、打分改动后的过期提示、轮次钳制（999→100、2→5）。

20　描述符框架导入导出（算法通用、底料本地）

解决什么问题

设计目标是「要通用工具，但也要落地」。描述符树此前是写死在代码里的 19 个变量，「通用」停留在定位表述上。这一块把变量结构整体抽成可导入导出的 JSON：换一套行业或区域，同一套流程照跑；落地靠本地的数据与判断，通用性靠这一层。

v1.3 文档在「通用性与落地」一节末尾写着「一键导入另一套分类框架的界面尚未做」。这一版做完了，那句话已从文档中撤掉。

怎么实现

  • JSON 结构：descriptors 数组，每项含名称、类型（输入型 / 参数型 / 结果型）、状态数组（≥2 个）、可选数值区间、界面分组。区间随框架一起走，导出再导入不丢。导出 exportFramework()，导入 importFramework()，重命名与序列化 fwName() / fwJSON()，扁平化 flatDescs()。
  • 导入校验：applyFramework() 逐条检查——非 JSON、不足 2 个描述符、状态少于 2 个、类型非法、重名，逐一当场报错，不带病运行。
  • 切换即清场：换框架等于换了一套变量，旧的选择、打分、已知值、全部分析结果一并清空，不留半套旧状态混进新框架。

边界

导入的 JSON 只带变量结构（描述符、状态、区间），不带判断——换框架后打分必须重做，这是方法决定的，不是没做完。政策库映射不随框架走：新框架的描述符在政策库中覆盖数为 0，属正常现象，界面已如实显示。

验证

test_fw.js 十七项——五类非法输入逐一拒绝、合法导入后描述符 / 分组 / 选择 / 打分 / 结果 / 区间逐项核对、导出往返、恢复原框架、示例框架载入。

21　贝叶斯后验（真的参与计算）

纠正了什么

v1.3 之前，「叠加贝叶斯」只是一个开关：打开后界面文案从「仅定性叙事」变成「贝叶斯（给区间）」，报告里也印出「叠加贝叶斯方法」，但代码中没有任何后验计算——这是对外承诺了没做的事。现在这条开关会真的改变计算结果。

模型

  • 观测：每条判断（一个描述符影响另一个）背后有一个潜在影响值 μ；专家在 −3…+3 的七档量表上打分，等于把 μ 切档后的读数。多人模式下每位专家各给一个读数，按各自置信度定噪声（BAYES_SD：高 0.55 / 中 0.85 / 低 1.25，app.js 第 4377 行）。
  • 先验：μ ~ N(0, 2.2²)，覆盖整个量表但很弱——没有假装有历史分布，这是弱信息先验，可在论文中如实写明并可替换。
  • 似然：七档切点取 −2.5/−1.5/−0.5/0.5/1.5/2.5（BAYES_CUT，第 4378 行），读数为 k 的概率 = 正态落在该档区间的质量。正态累积分布由 normCdf() 提供（第 4380 行）。
  • 后验：在 [−3.25, 3.25] 上按 0.05 网格做数值积分，输出后验均值、标准差、5%/95% 分位、P(μ>0.5)、P(μ<−0.5)。

怎么用

  • 后验均值矩阵替换原打分参与 CIB 一致性检验（状态级精判优先于描述符级后验，取值入口是 impactVal()）；开关一开，自洽集就会变——这是它与「标签」的分界。计算入口 computeBayes()（第 4419 行），渲染 renderBayes()（第 4444 行）。
  • 区间最宽的若干条判断单独列出（bayesWidest()），作为人审优先级；「方向判不准」的判据是任一方向都未达到 80%，这样既能抓平后验（质量堆在 0 附近），也能抓双峰后验（两位专家 +3/−3 时两侧各 13%、中间 74%）。单格翻转计数走 bayesFlipN()。
  • 报告与配置摘要里的表述改为「贝叶斯后验（有序 logit，含 90% 区间）」，不再写「叠加贝叶斯方法」这类含糊说法。

边界

后验给的是判断的区间，不是模型参数的区间——参数区间来自状态定义（见第 7 节），两者不要混为一谈。单人模式下只有一条观测，后验主要由先验与置信度决定，区间偏宽是正常的；它衡量的是「这条判断有多不确定」，不是「这个值有多准」。状态级精判仍按原值参与计算，尚未做逐格后验。

验证

test_bayes.js 七项——单条高置信 +3 的后验显著为正且下界大于 0；同分下高置信区间更窄；+3/−3 分歧呈双峰、无方向占优；同向两条比单条更集中；后验覆盖全部已打分条目；开关确实改变 impactVal 返回值；区间排序与判不准计数。

22　参数生成（四种方式，数值不再写「待定」）

解决什么问题

检验做完，下一步是把结论交出去。v1.3 的导出只有两种结果：GCAM 给的是 ScenarioComponents 装配清单，CHEER 给的 CSV 里 value 列写死「待定」，单位为空。结构对、数值空——挂上去跑不起来，还容易被误读成已完成。

v1.5 把参数生成从两种扩成四种，并且拆开了一个被捆在一起的概念：原先 useBayes 一个布尔同时管「后验要不要参与检算」和「导出成什么形态」两件事，现在这是两条独立的设置。

四种生成方式

名称由 GEN_LABEL 定义（app.js 第 273 行），界面由 renderGenOut() / renderOutBtns() / syncGenOpts() / setExpMode() 驱动：

方式产物用途
模型配置文件GCAM 装配清单 XML / CHEER 配置 CSV直接挂到模型运行目录；数值写在注释或 value 列里
结构化参数表CSV，表头 scenario,param,value交付给下游，按情景整组取用
定性叙事文字段落（narrText()）写进报告或论文正文
贝叶斯概率分布CSV，含后验均值与分位（bayesCSV()）需要区间而不是单点值时使用

取数规则

  • 对每个已选描述符取其选中状态的区间 lo / hi / 单位（跟随当前辖区口径，省级覆盖优先，由 paramOf() / expRows() / expLabel() 组装）。
  • 取档方式由用户明确选择：区间下界（保守）、中点、上界（加码）——平台不替用户默认选边，选择会写进导出文件的表头注释。
  • 年份锚点统一写 2035；文件头注明「2025 / 2030 需按政策里程碑插值」，不假装已经插好。
  • 状态没有定义区间时，值留空并写「该状态未定义数值区间，需人工给值」——宁缺不编。

结构化参数表为什么增列情景号

表头从「一行一个参数」改成 scenario,param,value（tableCSV()，预览 preview()，下载 downloadTableBtn() / downloadParams()）。理由是：CIB 求出的是一组互相咬合的自洽组合，原先导成一行一个参数等于把耦合又拆回独立参数，下游按行取值会读出彼此矛盾的组合。带上情景号之后，下游知道"这几行属于同一个情景，要一起用"。

另外两处

  • 装配文件不再乱指：此前未匹配的描述符会静默兜底成 carbon_tax_*.xml。现在无法确定装配文件的描述符单独列在注释里，标明「需人工补齐」，不再给出错误路径。
  • 一键下载：downloadAll() 把当前方式的全部产物打包下载；单文件下载走 download() / dl()，命名与标签由 fmtTag() 生成。

边界

本版只覆盖 2035 单锚点，且 GCAM 的 XML 只到装配清单层——不写具体的参数节点，因为不同变量在 GCAM 里的节点路径不同，臆造会产出语法合法但语义错误的文件。下一步是拿本地 GCAM-China 的真实 configuration.xml 与各 XML 文件核对，把 19 个描述符的装配文件与节点路径补全。

验证

test_export.js 七项——中点 / 下界 / 上界取值正确且落在区间内；CSV 含描述符与实测值、不含「待定」；CHEER 列数一致；GCAM 注释带数值、已知项路径保留、未确认项明确列出、不再出现 carbon_tax 兜底。参数表另由 test_par.csv 相关的成品级检查覆盖。

23　全局互斥对与孤立档位（矛盾面板的口径改写）

解决什么问题

「哪两档凑不到一起」是判断体系里最值得反复看的一类结论。v1.3 的矛盾组合面板只看用户当前选中的档位——没选的档位里的矛盾就看不见，等于把一份全局结论缩小成了一次局部检查。

v1.5 改为过所有描述符对的全部档位组合，列全部互斥对，不再依赖用户选了什么。

怎么实现

  • 互斥对：exclPairs() 扫全部描述符对与档位对，列出「两档各自都能出现在某个自洽情景里、但从不同时出现」的组合；上限 40 对，超出时界面标注已截断。渲染在 confList()，逐条折叠 toggleConf()，一键把某一对调开走 applyConfFix()；confPairs() 与 coFn() 提供计数与配对索引。
  • 孤立档位：aliveTable() 记录每个档位在自洽集里出现过没有，没出现过的是「孤立档位」，频率统计在 freqOf()。
  • 两者不同义，源码注释里专门写清了这一点：孤立档位是这一档自己站不住（在任何自洽情景里都不出现），互斥对是两档各自都行、凑一起不行。前者指向档位定义或区间可能有问题，后者指向一条真实的取舍。

实际效果

不选任何档位时也能看到整份互斥清单——它更像"这套判断体系的固有张力表"，而不是某次配置的检查结果。40 对的上限是展示取舍：超出部分更该回到打分矩阵去看，而不是在列表里堆到几百行。

验证

test_excl.js（第 31 套，2026-10-25 补）专测这一带，编号 1—12 共 14 个分组、26 项断言：口径与数据来源——没跑检验时不给假结论、自洽集为空时说无法判断、只有一个描述符时说样本不够、互斥对真的来自自洽集而不是写死的表、报出的每一对都确实从未共存且没有把「共存过」误报成互斥、判定与用户手选状态无关（全局口径）、自洽组数透传给界面；孤立档位——从未在任何自洽情景里出现过才算孤立、孤立档位不在互斥对里重复计入（互斥对两端都必须「活着」）、两者同时存在时各自计数正确；渲染与截断——互斥对数超过 40 时截断并标注「此处列出最值得看的 40 对」与总数、抽样时输出「可能把没抽到误判成不可能」而精确计算时不出现、自洽集为空时给可操作指引（复核打分矩阵 / 放宽锚定）、未跑检验时只给运行入口（runCIM()）而不给假结论。test_conf.js 测的仍是旧口径的 confPairs()（当前勾选档位内的矛盾与建议），不是本节的全局互斥对。

24　界面整体重做（v1.4 的主要工作）

解决什么问题

导师对 v1.3 的意见是「界面主次不清、凌乱、堆了很多功能」。这不是审美问题，是读者找不到主次：字号都在同一档、常驻说明比正文还多、七步横排在窄屏上退化成小圆点。

五条改动

  • 配色换「纸墨」：弃用 Tailwind 默认绿 #166534——它与大量 AI 生成页面同款，且绿色同时承担品牌色与「促进」语义，一旦某个词用绿、另一个含义也用绿，颜色就不再是信息。改为纸白打底、靛青做结构色、赭石做强调色。打分矩阵改用「靛—纸灰—赭」单调明度色阶：促进与抑制由明度与色相共同表达，与品牌色脱钩。
  • 字号从 12 种收到 6 档（11 / 13 / 15 / 16 / 21 / 30），正文从 11.5px 提到 15px。原先 182 处字号挤在 10.5–12.5px，层级几乎不存在——这才是「凌乱」的技术原因。
  • 横向七步改左侧步骤轨：七步横排时每格只有一百多像素，只能退化成小圆点；改为左轨后可显示序号、名称与完成状态，顶栏六个按钮收进图标入口。步骤名由 STEP_NM 提供（app.js 第 1982 行）。
  • 常驻小字改悬停或折叠：原先界面常驻约 2500 字说明（20 段，平均每段 111 字），读者会训练自己忽略所有小字、连警告一起忽略。现在一屏常驻说明为 0；警告与冲突提示仍常驻，不进悬停——这条是自觉的例外。
  • 新增「怎么用」入口（openHelp()），首页七行对比表按「政策→参数 / 参数→情景 / 情景→模型」压成三行。

实际效果

主次靠字号、颜色与常驻信息量三层同时收：字号给层级，颜色只承担一种语义（促进 / 抑制），说明文字按需出现。功能没减少，减少的是同时出现的东西。

验证

界面改动本身以视觉检查为主；可机器守的部分由 test_home.js（首页统计条四项来自真实数据、组合数按亿 / 万换算、旧演示数据与写死的对比表不得复活、首页矩阵 81 格）与 test_menu.js（第 7 步 10 块归类、标签 3 个、折叠段默认收起）守。

三个约定：脚本本身是 ASCII-only（Windows PowerShell 5.1 会把无 BOM 的 .ps1 按 ANSI 读，中文会解析失败，所以任何中文都不要加进去）；-Repo 与缺省是二选一，分别指归档副本与工作区源码，不是叠加；-Prod 缺省时成品冒烟会被明确报成 skipped（不跑就是不跑，不会混进「全部通过」）。脚本里没有基线、白名单或豁免名单，30 套源码级自检当前全部零 ✗。历史版本的测试不复制到各版本目录，统一挂在归档的 platform/v1.5/tests/（工作区另有同一份 _src/ 副本，不在仓库内）。

发布流程

改一次就发一次：在本机工作副本改完 → 跑自检（31 套全过才继续）→ 合并成单文件并写进仓库（--repo 会同时更新 platform/<版本>/ 与本仓库根 index.html）→ 提交推送，Pages 约 1 分钟后自动更新。

  1. 只有一场面谈有录音进工作区：_src/mtg_rec.txt（553 段）与 _src/mtg_min.txt（69 段）经记忆日志确认属 2026-10-16 那场。09-24、10-09、10-21 三场的录音 / 纪要 docx 都存放在桌面资料库或微信文件夹，不在本工作区，本文件对这三场的记录全部是记忆日志的转述，不是录音原文。
  2. 10-17 那场没有发生：记忆日志曾写「导师已把交流定在明天（10/17 周六）下午 15:30—16:30」，次日被明确更正为顺延到 10-21 下午 3 点后；更正时作者自陈「把顺延后的日期记成了原定日期」。讨论日志不收录 10-17 面谈。
  3. 09-17 面谈的日期是推断的：工作区没有该场纪要，仅由两篇日志前后夹逼。
  4. 「发言人身份」靠日志认定：录音只标「发言人1/2/3」，导师与两位同学的对应来自记忆日志，录音原文中未出现姓名。
  5. 引号内容的可靠度分级：_src/mtg_rec.txt / _src/mtg_min.txt 的引语可回溯到录音段落号，可靠度最高；.workbuddy/memory/*.md 里带引号的导师原话是 AI 助手在会话中记录的，可能经过整理，未经录音原文复核。
  6. 09-24 的批注没有原件：6 处黄色高亮批注的原文抄录自记忆日志，批注所在的两份报告 docx 后被编辑器打开保存过一次、体积变化（39,872→41,238；53,085→53,574），日志称高亮完整保留但未再复核。
  7. 无法确认的日期细节：10-09 面谈的具体开始时间、10-21 面谈的具体开始时间，工作区材料里都没有；只有「下午 3 点后」「15:30」这类约定，不是实际开始时间。
