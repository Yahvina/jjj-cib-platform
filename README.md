## 关于「亮点」的判定口径

切出的 8 个模块分两类来源：

**① 本版设计上最关键的两处：**

- **H1 功能对比首屏** —— 对应「第一页必须讲清楚对方的痛点」；
- **H2 从政策数据库拉取预设** —— 把「手工逐条定义状态」变成「从数据自动预填」，是本版最直接的一个卖点。

**② 从方法完整性与工程价值判断为本版最扎实的：**

- **H4 翻译依据与时间锚点** —— 直接回应「参数说不清依据」的质疑；
- **H5 判断链** —— 回应「要有评分的过程」这一要求；
- **H6 矛盾闭环** —— 发现矛盾之后还能给建议并重检；
- **H3 三层差异预览** —— 「多尺度」在界面上的具体落点；
- **H7 双锚点时间轴** —— 2030 政策锚点 / 2035 情景锚点的口径固化；
- **H8 真实结构导出** —— 导出的是 GCAM 真实 `ScenarioComponents` 结构，不是自造格式。

索引页 `highlights/index.html` 里有每一项的详细说明。

## 使用方法

**看平台**：双击 `index.html`，用浏览器打开即可。单文件、零依赖，不联网也能跑。

**取用某个亮点**：
1. 引入 `highlights/_shared/base.css`（含全部设计令牌）；
2. 把模块的 `fragment.html` 复制进页面结构；
3. 引入模块的 `logic.js`，在页面加载后调用其渲染入口。

## 发布流程（改一次就发一次）

平台源码的**工作副本在** `C:\Users\guiqu\WorkBuddy\2026-09-16-21-47-56\_src\v15\`（`index.html` + `src/app.js` + `src/styles.css`），本仓库里的是**归档副本**。改完一处就按下面三步走，线上始终等于仓库里的成品：

```powershell
# 1. 在本机工作副本改完，跑自检（30 套，全过才继续）
cd C:\Users\guiqu\WorkBuddy\2026-09-16-21-47-56\_src
foreach($t in Get-ChildItem test_*.js){ node $t.Name v15/src/app.js }   # test_menu/test_doc 传 v15/index.html

# 2. 合并成单文件并写进仓库（--repo 会同时更新 platform/<版本>/ 与本仓库根 index.html）
python merge_v15.py --repo

# 3. 提交并推送（Pages 约 1 分钟后自动更新）
cd ..\jjj-cib-platform
git add -A; git commit -m "简述这次改了什么"; git push origin main
```

**`--repo` 不能省**：不带它时只写桌面与工作区 `output/`，仓库与线上都不会动。带它时会自动做三件事——写 `platform/<版本>/` 单文件成品、镜像分文件源码、**把仓库里的源码重新合并一遍并断言与成品逐字节相同**（防止仓库源码与线上成品变成两套东西），同时把 30 套测试一起归档。

**版本号三处绑定**：`merge_v15.py` 的 `VER`、成品文件名 `NAME`、`index.html` 的 `<title>`。改版本号要三处一起改，否则发布出去的成品与归档目录对不上。

**验证发布成功**：`git rev-parse HEAD` 与 `git rev-parse origin/main` 相等即已推送（推送时 PowerShell 可能因 `git` 往 stderr 写进度而报 `NativeCommandError` / exit 1，**那是显示问题不是失败**，看哈希相等即可）。线上确认：打开 https://yahvina.github.io/jjj-cib-platform/ ，标题栏应显示对应版本号。

**逐层求解**（跨层约束真正进入求解）：区域级解出的每个自洽情景，其取值转成下级的约束——下级与它<b>区间不相交</b>的状态直接不进枚举，而不是算完再比对档位差。上级定「目标节奏（20–30%）」，下级「快速清洁化（30–40%）」根本不会被算到。上级某情景若让下级完全无解，会单独计数——<b>那不是程序出错，那就是结论</b>。输出为带完整层级路径的组合（区域情景 → 省情景 → 0、却存在间接通路</b>的配对——它们提示矩阵里可能漏了一条关系。跨层传导（国家目标 → 省域结构 → 市级排放）本质就是路径问题。<br>⑫ **影响谱**（对应德国软件的 Influence profile）：把每个状态逐个「钉死」、重算自洽情景集，再与基准对比，看这条外部冲击<b>挤掉</b>了哪些可能；整行为 0 系数衡量两个状态在自洽情景里是否总是同进同出（＋100% 同进同出、−100% 此消彼长）。只算<b>跨描述符</b>配对——同一描述符的不同状态天然互斥，φ 恒为 −100%，不是信息。情景数少于 20 时界面会警示「系数可能不稳定」（手册原话 may lead to artificial results），并附单个状态的<b>关联谱</b>。<br>⑭ **演示模式**（对应德国软件的 ## 当前状态与边界

**已经能真跑通的**：七步流程、描述符树勾选、状态设置（含取值区间编辑、状态重命名、增删自定义状态）、政策库浏览与映射查看、按政策库预填来源、上传政策清单、交叉影响打分（可编辑矩阵、AI 预填、置信度审核留痕）、**多专家集成**（多份矩阵分人打分、分歧识别、逐条裁定或一键取中位数、导出集成工作簿）、影响平衡预览、**一致性检验真实算法**（枚举状态组合 → 算影响平衡 → 按一致性原则筛自洽情景；组合数超 20 万自动改抽样）、影响关系图、主被动图、情景表、**情景地图**（情景族聚类图 / 状态分布热力图）、情景报告（HTML / JSON 双出口）、翻译依据展开、判断链展开、矛盾建议采纳、配置导出（真下载文件）、保存 / 载入（含打分矩阵与多专家状态）。

**仍为占位或待完善的**：
- 交叉影响判断的**记录单位仍是描述符对**，状态级为可选精判（已支持，但需要人工逐格填）；未精判的部分仍按整体倾向自动展开；
- **跨层一致性是独立校验，不并入 CIB 的组合枚举**：纵向相容（档位不反向）已在第 7 步实现为独立检验；层级树虽有 4 层，但**国家级是给定层不参与枚举**，实际枚举 3 层。若把国家级也当变量，6 个描述符下组合数会从 3¹⁸（≈3.9 亿）涨到 3²⁴（≈2824 亿），差 729 倍；
- **数值加总校验暂未做**：北京、天津、河北是三个平级单位，而市级只覆盖河北，层结构不同构——"下级之和能否凑出上级"的前提不成立，需先厘清层级树的构成；
- **跨层约束的具体形式是我们自研的设计假设**（档位差 ≥ 2 判冲突），导师从未定义过，待当面确认；
- 多专家比对仅按条目汇总，暂未给出专家间的一致性系数（如 Kappa）等统计量；
- 政策库的路径—描述符映射为模型侧首版判断，置信度"中/低"的条目待补政策原文依据；
- 各状态取值区间的依据分四类并在界面上标注：**政策目标 3 个**（一次能源结构、钢铁工艺路线、单位产品能耗限额强度）、**需换算 5 个**、**示例值 9 个**、**外生输入 2 个**。示例值的区间需按实际研究口径校准；
- **数值锚定的前提是区间可信**：锚定按"区间与锚定值是否相交"判存否，若区间本身是示例值，锚定的结论也只到示例精度；单位不同的描述符需各自填写同单位的值。

平台界面上已主动标注了这些边界。
