### 亮点模块是从源码生成的，不是手工摘抄的

上一版 8 个模块是 2026-10-16 手工从 v1.0 切的，切完之后平台又改了四版，副本就没人管了——引用着已删除的函数（`pullDB`、`applyFix`、`csvParam`）、配着已经弃用的蓝绿配色、标着 v1.0 的行号。手工切一次就必然过期。

现在改成从源码切：

```powershell
cd highlights
python build_highlights.py          # 重新生成全部模块
python build_highlights.py --check  # 校验是否与源码一致（退出码 1 = 过期）
```

`--check` 是给发布流程用的：它把每个文件应有的内容在内存里算出来逐字节比对，改了源码却忘了重建、或者源码里挪掉了某个被引用的函数（锚点找不到直接报错），都会让它失败。**`python merge_v15.py --repo` 会自动调它**，过期就发不出去。

## 关于「亮点」的判定口径

8 个模块分两类来源：

**① 导师当场点名、设计上最关键的两处：**

- **H2 政策库与映射** —— 导师当场夸赞的一处：「我觉得你这个特别好，从政策库拉取预设」。它把「手工逐条定义状态」变成「从数据自动预填」，是本平台最直接的一个卖点。
- **H3 各层差异预览** —— 「多尺度」在界面上的具体落点：同一套描述符在国家级／区域级／省级／市级口径不一样，第一步就把这张表摊开。

**② 从方法完整性与工程价值判断为最扎实的：**

- **H4 描述符状态面板** —— 直接回应「参数说不清依据」的质疑：状态挂区间、依据有出处、已知值当下限；
- **H5 自洽情景的判定** —— 回应「要有评分的过程」这一要求，能一路点到某条判断为什么这么打；
- **H6 矛盾组合与处理建议** —— 发现矛盾之后还能给建议并重检，是个闭环；
- **H7 逐层求解** —— 国家级 / 区域级 / 省级是嵌套的，下层取值真的受上层约束；
- **H8 四形态导出** —— 导出的是 GCAM 真实 `ScenarioComponents` 结构，且参数表带情景号，不把耦合拆散；
- **H1 首页一屏** —— 「第一页必须讲清楚对方的痛点」；四个统计全部现算，没有一个写死的估值。

索引页 `highlights/index.html` 里有每一项的详细说明。

## 使用方法

**看平台**：双击 `index.html`，用浏览器打开即可。单文件、零依赖，不联网也能跑。

**取用某个亮点**：
1. 引入 `highlights/_shared/base.css`（含全部设计令牌）；
2. 把模块的 `fragment.html` 复制进页面结构；
3. 引入模块的 `logic.js`，在页面加载后调用其渲染入口。

## 发布流程（改一次就发一次）

源码就在本仓库里：`platform/v1.5/`（`index.html` + `src/app.js` + `src/styles.css`）。改完按下面走，线上始终等于仓库里的成品。

```powershell
# 1. 跑自检（33 套，全过才继续）
powershell -ExecutionPolicy Bypass -File platform/v1.5/tests/run_tests.ps1 -Prod

# 2. 若动了平台源码：重新生成亮点模块（忘了这步发布会被闸门挡住）
cd highlights; python build_highlights.py; cd ..

# 3. 合并成单文件并更新仓库根 index.html（会在写文件前先做全部断言）
python merge_v15.py

# 4. 提交并推送（Pages 约 1 分钟后自动更新）
git add -A; git commit -m "简述这次改了什么"; git push origin main
```

`merge_v15.py` **自己认布局，不用传路径**：在仓库里跑就更新 `platform/v1.5/` 成品与仓库根 `index.html`；在带 `_src/v15/` 工作副本的目录里跑则写 `output/` 与桌面副本，加 `--repo` 才写仓库。

它在**写任何文件之前**先做完全部断言，并额外做两件事：**把仓库里的源码重新合并一遍、断言与成品逐字节相同**（防止仓库源码与线上成品变成两套东西），以及**校验亮点模块与源码一致**。任一项不过就整体拒绝，仓库不留半成品。

`--check` 可单独跑：`python merge_v15.py --check`（只校验、不写任何文件）。

**版本号三处绑定**：`merge_v15.py` 的 `VER`、成品文件名 `NAME`、`index.html` 的 `<title>`。改版本号要三处一起改，否则发布出去的成品与归档目录对不上。

**验证发布成功**：`git rev-parse HEAD` 与 `git rev-parse origin/main` 相等即已推送（推送时 PowerShell 可能因 `git` 往 stderr 写进度而报 `NativeCommandError` / exit 1，**那是显示问题不是失败**，看哈希相等即可）。线上确认：打开 https://yahvina.github.io/jjj-cib-platform/ ，标题栏应显示对应版本号。

## 当前状态与边界

**已经能真跑通的**：主界面三步（选政策 → 确认设定 → 看结果并导出），原七步流程整体收进「研究模式」；描述符树勾选、状态设置（含取值区间编辑、状态重命名、增删自定义状态）、政策库浏览与映射查看、按政策库预填来源、上传政策清单、交叉影响打分（可编辑矩阵、AI 预填、置信度审核留痕）、**多专家集成**（多份矩阵分人打分、分歧识别、逐条裁定或一键取中位数、导出集成工作簿）、影响平衡预览、**一致性检验真实算法**（枚举状态组合 → 算影响平衡 → 按一致性原则筛自洽情景；组合数超 20 万自动改抽样）、影响关系图、主被动图、情景表、**情景地图**（情景族聚类图 / 状态分布热力图）、情景报告（HTML / JSON 双出口）、翻译依据展开、判断链展开、矛盾建议采纳、配置导出（真下载文件）、保存 / 载入（含打分矩阵与多专家状态）。

**仍为占位或待完善的**：
- 交叉影响判断的**记录单位仍是描述符对**，状态级为可选精判（已支持，但需要人工逐格填）；未精判的部分仍按整体倾向自动展开；
- **跨层一致性是独立校验，不并入 CIB 的组合枚举**：纵向相容由逐层求解承担（上级某档与下级某档取值区间完全不相交时，下级该档不进枚举）；
- **数值加总校验暂未做**：北京、天津、河北是三个平级单位，而市级只覆盖河北，层结构不同构——"下级之和能否凑出上级"的前提不成立，需先厘清层级树的构成；
- **跨层约束的具体形式是我们自研的设计假设**（区间完全不相交即判冲突），导师从未定义过，待当面确认；
- 多专家比对仅按条目汇总，暂未给出专家间的一致性系数（如 Kappa）等统计量；
- 政策库的路径—描述符映射为模型侧首版判断，置信度"中/低"的条目待补政策原文依据；
- 各状态取值区间的依据分四类并在界面上标注：**政策目标 3 个**（一次能源结构、钢铁工艺路线、单位产品能耗限额强度）、**需换算 5 个**、**示例值 9 个**、**外生输入 2 个**。示例值的区间需按实际研究口径校准；
- **数值锚定的前提是区间可信**：锚定按"区间与锚定值是否相交"判存否，若区间本身是示例值，锚定的结论也只到示例精度；单位不同的描述符需各自填写同单位的值。

平台界面上已主动标注了这些边界。
